## Contradiction matrix

**HIGH — GAP-M: `trader-spec.md:244` presents a decided question as open, and quotes the two options ADR-0015 explicitly forbids quoting as live.**

The spec's ADR-0018 D5 block ends:

> **Open, and not decided here:** ADR-0018 D5's fractions are calibrated to a **£750 equity leg**. With crypto out of scope, ADR-0015's £750/£750 split no longer describes the book, and whether the equity leg takes the full £1,500 doubles the absolute loss at the same percentage envelope — on a subclass already overshooting. ADR-0015's amendment records this as needing its own decision before the live ramp.

`docs/adr/0015-live-venue-account-and-book-split.md:119` answers exactly this question and forbids exactly this quotation: **"ANSWERED 2026-08-18 … do not quote the £750/£1,500 options as live."** The 2026-08-18 amendment re-bases the total book from £1,500 to £1,000, all equity; `EQUITY_LEG_FRACTION_OF_CAPITAL` is **deleted, not set to 1.0**; and D5's fractions resolve against the whole account unscaled to **£350 (index) / £250 (single-stock)**. The resolution is neither of the two branches this paragraph still poses as open.

This is HIGH rather than MEDIUM because it is not a stale number in an aside — it is a spec paragraph headed **"Open, and not decided here"** sitting on the live sizing path, which instructs the next reader (and the `/to-tickets` pass) to treat a settled book decision as a blocker still to be resolved. It is also self-falsifying on its own terms: the "needs its own decision before the live ramp" clause pointed at **#798**, which is **CLOSED** (the 26.2%/41.8% envelope was accepted, and `risk-manager-spec.md:236` already records that acceptance).

**Fix:** replace the bullet with the decided state — the book is £1,000 all equity, D5's 35%/25% resolve to £350/£250 unscaled, `EQUITY_LEG_FRACTION_OF_CAPITAL` is deleted — and cite ADR-0015's 2026-08-18 amendment. If a residual concern is wanted, it is that #798 accepted a 41.8% single-stock drawdown against `CONTEXT.md`'s 20–25% band, which `risk-manager-spec.md` already states; that is an accepted overshoot on the record, not an open decision. Owner: `trader-spec.md`, which is the spec that carries the conversion arithmetic.

**No other cross-spec type or field contradiction was found.** The registry's ten sections were diffed against every extract that defines or consumes them and all ten hold — see Confirmed clean.

## Security findings

**MEDIUM — GAP-N: `shared-sqlite-store-spec.md` asserts the crash-restart invariant but specifies no transaction boundary for the multi-table writes that invariant depends on.** The spec's only named crash-safety mechanism is `"WAL mode + synchronous=FULL gives crash-restart safety without meaningfully taxing this system's tick-based (not HFT) write rate."` That buys durability of a *single committed write*. It does not buy atomicity across the fill-lands-in-`fills` + `open_positions`-is-updated pair, which is precisely the pair CONTEXT.md's "crash-restart must not lose open positions" invariant is about. A crash between those two statements leaves a recorded fill against a position row that does not reflect it — with real money and no human watching (ADR-0013). **Fix:** state explicitly that every write touching more than one of `open_positions`/`fills`/`closed_trades`/`flatten_submissions` runs inside one `BEGIN…COMMIT`, and name the seam that enforces it (the `SharedStore` handle, not each caller). Owner: `shared-sqlite-store-spec.md`; Execution is the sole writer of all four tables, so the boundary is enforceable in one place.

**MEDIUM — GAP-O (aggregate, three specs): the boot-time-only auth flag.** `dashboard-spec.md:570`'s `SAMURAI_DASHBOARD_TOKEN` gates the boot-time bind and is never verified per request — it is an acknowledgement flag, not a credential. Already tracked as **#1038 (open)**; referenced here because two adjacent specs share the shape: `transport-layer-spec.md` and `verdict-spec.md` both state plainly that `TELEGRAM_ALLOWED_USER_IDS` is the *sole* working access control on approving a live-money trade and that the `SignedApprovalChannel` HMAC is decorative under polling transport. Those two are correct and honestly documented (an empty allowlist fails closed; a permissive one is flagged as critical exposure) — the cross-spec observation is only that the system now has two independent single-string boot-time gates in front of money-adjacent surfaces, and only one of them (#1038) is ticketed. **Fix:** no new spec change required; when #1038 is worked, decide whether the dashboard's answer (per-request verification) should also be the shape for any future non-polling approval transport, so the two do not diverge.

**LOW — `transport-layer-spec.md` specifies no runtime failure contract for an alert send that itself fails.** The spec is thorough on `SAMURAI_ALERTS` having no default (fail-closed at boot) and on the approval-timeout fail-safe, but never states what happens when `sendMessage` fails mid-run against a Telegram outage — swallow, retry, or block the tick. Adjacent open issues #1130 (escalation posted over the down channel) and #1131 cover parts of this at the code level. **Fix:** one sentence: a failed operational-alert send is logged and swallowed, never blocking or failing a tick, with the failure recorded in `alert_delivery_failures`.

**LOW — `market-intelligence-spec.md`: `wrapUntrusted` cannot reach X/Grok post bodies**, because those enter the model server-side via the search tool rather than through an interpolated prompt block. This is a real limit of the mitigation, not a defect in the spec's reasoning; the risk-manager critic path shows the correct containment pattern (the model can only *propose* a condition; deterministic code does the checking). **Fix:** state the limit explicitly in `market-intelligence-spec.md` so a reader does not assume `wrapUntrusted` covers the retrieval path, and note that MI output is advisory input to debate, never a gate.

## Design-practice findings

**MEDIUM — GAP-P: no spec owns entry-price feasibility, and the two specs that could each assume the other does.** `universe-selector-spec.md` ranks on the **US underlying's** reach rate and shortlists the **LSE ETP** — and is silent on share price throughout: no mention of £350/£250, of the per-position cash ceiling, or of whole-share sizing. `risk-manager-spec.md` refuses below the min-viable floor but has no upper price gate, and `trader-spec.md` sizes from a fraction with no feasibility check. The result is a shortlist that can contain a name whose ETP price exceeds the per-position cash cap, which cannot be entered at all — one whole share does not fit. **#1136 (open)** measures whether whole-share sizing floors real paper entries to zero, and **#1002 (open)** covers pool priceability, so the *measurement* is ticketed; what is not is the **ownership question at spec level** — no spec claims the feasibility gate, and this is the same silent-delegation shape `cross-verify-2026-08-26.md`'s GAP-L caught on held-position earnings. **Fix:** name the owner explicitly. The screener is the natural home (it already applies a liquidity gate over `saxo_tradeable` and already constructs its own data client), so add a price-feasibility clause to `universe-selector-spec.md`'s candidate-pool section stating that a row whose current price exceeds the subclass per-position cash cap is excluded pre-ranking — and say so even if the implementation lands via #1136.

**MEDIUM — GAP-Q: `shared-sqlite-store-spec.md` lists `cii_snapshots` under Market Intelligence ownership, but the spec itself records "no writer in code yet", and MI's own store is a separate file.** An orphaned table with a named owner that does not write it is the `DebateLog` shape the registry's own history warns about, inverted. **Fix:** either assign MI the write explicitly (and ticket it) or mark the table dormant-by-decision in the spec so a reader does not infer a producer exists.

**MEDIUM — `risk-manager-spec.md`'s critic invocation couples the caller to a sentinel string.** `buildRiskStep` evaluates once with no verdict and consults the critic only if that pass pushed `RISK_CRITIC_SKIPPED_REASON` into `reasons` — i.e. "we reached step 7" is signalled by matching a magic string in a `string[]`. Renaming or rewording that reason silently disables the critic, with no compile error and no test that would necessarily catch it (the mechanical pipeline still produces a valid decision). **Fix:** return the step-7 signal as typed data — a discriminated `PendingCritic` variant, or a `reached_critic: boolean` on `RiskDecision` — so the coupling is compiler-enforced. This is the "tested mechanism nothing calls" class this repo hits repeatedly.

**MEDIUM — `feedback-loop-spec.md`: `runDailyCycle` has no idempotency key and no minimum-sample floor.** Two runs for the same cycle date can both step the dials (there is no dedup key comparable to Execution's `idempotency_key` or `daily_equity`'s `ON CONFLICT DO NOTHING`), and no stated minimum number of closed trades gates a weight adjustment, so a two-trade day can move analyst weights. **Fix:** key the cycle on `cycle_date` with first-write-wins (the `feedback_cycle_schedule` table is already the natural home), and state a minimum closed-trade count below which the cycle records "insufficient sample" rather than stepping.

**MEDIUM — `market-data-service-spec.md` specifies no vendor fallback or retry behaviour, and there is still no LSE mark source.** The service is the sole mark provider for Risk and Verdict, both of which fail closed on a stale mark — so vendor behaviour on failure is load-bearing for whether the system trades at all. `#895` (open) still owns picking and provisioning the LSE vendor. **Fix:** state the per-vendor failure contract (retry policy, and that an unavailable mark surfaces as unavailable rather than as a stale value), and keep #895 cited in the spec as the blocking dependency it is.

**LOW — `universe-selector-spec.md` and `market-intelligence-spec.md` each specify a downstream degrade but not a vendor-call failure mode.** The screener specifies what happens to a stale watchlist (fall back to `fallback_default` rows, never an empty list — good) but not what happens if the Alpha Vantage `EARNINGS_CALENDAR` call itself 5xxs mid-run: no exclusions today, or the whole run treated as failed. This is open question 1 from `cross-verify-2026-08-26.md`, still unresolved. **Fix:** resolve it in the spec as "the run proceeds with no exclusions and alerts", consistent with the never-halt-silently philosophy the same spec already states.

**LOW — `t212_isa` survives as a pool-schema field name.** `universe-selector-spec.md` is explicit that the live gate reads `saxo_tradeable` and that `t212_isa` answers a wrong-venue question, so this is inert, not a defect. But the field name will read as a live venue claim to anyone grepping for T212 during the #946 follow-up. **Fix:** rename to something provenance-shaped (`t212_metadata_isa`) or drop it when the pool is next touched.

## Performance / maintainability / complexity / simplicity findings

**MEDIUM — residual crypto typing is now split three ways across the folder, and the inconsistency is the maintenance cost, not the types.** Crypto left scope 2026-08-16, and the specs have diverged in how they say so:

- **Annotated correctly** — `risk-manager-spec.md` (explains that the tiering dimension moved to `subclass`, and that `daily_loss_pct_by_class` now has one live class) and `universe-selector-spec.md` (every crypto clause struck with a dated withdrawal note).
- **Unannotated, crypto typed as live** — `verdict-spec.md` (`VerdictConfig.automation_level`/`max_signal_age`/`max_mark_age`/`drift_tolerance_pct` all keyed `'crypto' | 'stocks'`, and the drift-gate's fractional-not-absolute rationale is argued from a six-figure BTC-USD example) and `transport-layer-spec.md` (Alpaca crypto path-root routing, Polygon `BTC-USD` → `X:BTCUSD` translation, `VolatilityReading {crypto, stocks}`). Neither carries an amendment note on this axis.
- **Schema-level, deliberately generic** — `shared-sqlite-store-spec.md`'s `CHECK(asset_class IN ('crypto','stocks'))` across nine tables plus `risk_log.crypto_tripped`/`daily_pnl_crypto_pct`.

The schema case is defensible (a CHECK member costs nothing and a future crypto system inherits the shape). The two unannotated specs are the problem: a reader cannot tell whether `'crypto'` there is dormant-by-decision or live-and-forgotten. `#1157` (open) already covers the code-side crypto candle clients. **Fix:** add the one-line dated withdrawal note to `verdict-spec.md` and `transport-layer-spec.md` that the other two specs already carry — do not delete the union members, and do not re-argue the drift gate's fractional rationale, which is correct on its own terms.

**MEDIUM — `risk-manager-spec.md:234/236` anchors its worked cash examples on the superseded £750 leg.** Verbatim: *"At ADR-0015's £750 leg that is ~£262.50 and ~£187.50 at inception only"* and *"A frozen £262 is 34.9% of a £750 book, 43.7% of £600 and 58.2% of £450"*. On the decided £1,000 all-equity book these are **£350 and £250**. This is MEDIUM, not HIGH, and the distinction is worth stating precisely: **the mechanism is correct and not stale** — the config carries the *fraction* and the gate resolves it against `portfolio.equity` on every decision, which is exactly what ADR-0018 D5 specifies and what makes the second passage's fixed-cash-is-directionally-wrong argument sound. Only the illustrative anchors are stale, and the second passage's £600/£450 arithmetic is a rhetorical ladder whose conclusion survives re-basing. **Fix:** re-base both figures to £350/£250 against £1,000 and keep the argument intact; do not restructure the section.

**MEDIUM — `debate-engine-spec.md` is internally inconsistent on its own latency budget:** 30s at lines 21, 279 and 292; a stale, unannotated 15s at lines 354, 413 and 468. Line 290 records the correction (every crypto debate timed out at 15s on the first real paper tick, #581) and 292 decides 30s/1-round, but the test-plan bullet (354), the "Latency Budget Trade-offs" section (413) and the Resolved Issues summary (468) still carry the pre-#581 number with no supersession marker. Two numbers for one budget in one spec is the kind of thing an implementation ticket resolves by picking whichever it read first. **Fix:** 30s at 354 and 413 (they state the live budget); at 468, which is a historical record of what the wayfinder map decided, keep the 15s and mark it superseded by #581 rather than rewriting the decision log.

**MEDIUM — `stage2-validation-execution-spec.md` pins no seed for DSR/PBO resampling.** Both are resampling statistics on the selection-accounting path, and the whole point of Stage 2 is that the numbers are auditable and reproducible against a recorded verdict. An unseeded resample cannot be re-derived. **Fix:** require an explicit seed, recorded alongside the result in `config_trials`/`stage2_selected_config`.

**LOW — the same spec's header says "Executed" and its footer says "Ready for `/to-tickets`".** One of the two is wrong about the document's lifecycle state. **Fix:** header wins — it is executed; drop the footer line.

**LOW — `shared-sqlite-store-spec.md` specifies no `busy_timeout` and does not discuss SQLite's single-writer constraint under WAL**, while its own integration map names eight distinct writer components and the repo runs orchestrator, service-api and `tools/` scripts against one file. `#1131` covers `alert_delivery_failures` retention specifically; the general point here is contention, not growth. **Fix:** add `busy_timeout` alongside the WAL/`synchronous=FULL` pragma statement, and state which processes may write.

**LOW — unbounded append-only growth is specified for one table and not the rest.** `llm_call_log` has an explicit row-ceiling prune (#1045); `audit_log`, `bars`, `fills`, `debate_log`, `trader_log`, `risk_log` and `broker_observed_fills` have none (the last is explicitly flagged in-spec as deferred, and `#1059` covers its retirement). Not urgent at this system's write rate. **Fix:** state a retention posture per table, even if the posture is "unbounded, accepted".

## Confirmed clean

- **Frozen registry §1–§10 all hold.** `debate_id` is TEXT and a Debate-Engine-issued hash at all three consumers; `DebateResult`, `MarketDataService`'s four consumers, `MetricsSuite` (flat) vs `MetricsReport` (nested), `CostModel.fill`, and `Direction`/`DateRange` are consistent everywhere they appear.
- **Registry §4 — Execution is the sole writer of `open_positions`/`fills`/`closed_trades`, and `shared-sqlite-store-spec.md` states it in exactly those words.** No second writer claims any of the three. The one dual-writer table (`cosine_setups`: Trader at decision time, FL at close) is dual **by explicit design**, stated as such, not a conflict.
- **Registry §8 — invalidation conditions ride inside `RiskCriticVerdict`.** `risk-manager-spec.md` is emphatic that there is no `RiskInput.invalidation` field and no `InvalidationResult` crossing the stage boundary. The registry and the spec agree, and the declined 7th stage does not exist in either.
- **Registry §9 — threshold clamps (#638) are honoured.** `max_drawdown_pct` 0.44 against a hard in-code 0.45 ceiling, `recovery_drawdown_pct` 0.20, refused-not-coerced at construction, on every live `risk_thresholds` read, and on every Feedback Loop write.
- **The stage set is the authoritative six.** `orchestrator-spec.md` carries exactly Analysts → Debate → Trader → Risk → Verdict → Execution. `devils-advocate-spec.md` and `skeptic-self-review-spec.md` both carry correct, dated decline banners — neither reads as a live stage.
- **Exits and flat-by-close are not blocked by guards, in both stages that could block them.** `risk-manager-spec.md` returns at `intent_type === 'exit'` *before* the entry-cap loop is entered, so no gate and no throw inside one can reach a flatten; `verdict-spec.md`'s #826 amendment skips gates 2 and 3 together for `metadata.unpriced_exit`, and only for that. Both are the correct shape for the "Guards Before Early Returns" defect class, and both are stage-scoped honestly (Risk states plainly that a tripped breaker *can* stop a flatten one stage later).
- **No return-only benchmarking anywhere.** The control-arm and outside-benchmark tables both carry drawdown alongside return, per doc 12's D4.
- **Fractional-Kelly discipline holds.** `trader-spec.md` states "never full Kelly" and the fractions are measured, not tuned; the fat-tail conservatism moved from `AssetClass` to `subclass` rather than being dropped.
- **Point-in-time / completed-bars-only holds where it matters.** The screener is idempotent by construction (completed bars only, re-run produces the same watchlist) and `InstrumentRegistry` is deliberately *not* reused for the live pool because it answers a point-in-time backtest question instead.
- **`universe-selector-spec.md` does not conflate the screened instrument with the traded one.** `screening_instrument` (US underlying) and `lse_ticker` (what Samurai routes) are a deliberate seam, neither is defaultable from the other, the loader rejects a row missing either, and the routing map binds over `lse_ticker` only. SPY/QQQ/AAPL/TSLA are repeatedly and explicitly marked not tradeable.
- **The screener fails toward a bounded known-good subset, never an empty list.** An empty active universe would be a total trading halt presenting as a healthy system — the exact #625 signature — and the spec names that failure mode and closes it.
- **The risk critic fails open, and that is the safe direction here** — every producer-side failure yields no verdict, the decision keeps an explicit `risk_critic: skipped` reason, and the mechanical pipeline remains the safety net. A model cannot self-assert a breach: the raw-parse shape has no `state` field, on both first parse and replay.
- **Verdict is deterministic, calls no LLM and no broker**, and every gate failure maps to a distinct `no_go_reason` — clean auditability, no re-derivation of Risk's thresholds.
