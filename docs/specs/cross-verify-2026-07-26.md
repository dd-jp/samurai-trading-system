# Cross-Spec Verification Pass — 2026-07-26 (full, supersedes same-day partial pass)

Specs reviewed (folder: `docs/specs/`): `analysts-spec.md`, `cost-model-backtest-spec.md`, `dashboard-spec.md`, `debate-engine-spec.md`, `execution-spec.md`, `feedback-loop-spec.md`, `market-data-service-spec.md`, `market-intelligence-spec.md`, `orchestrator-spec.md`, `risk-manager-spec.md`, `shared-sqlite-store-spec.md`, `trader-spec.md`, `verdict-spec.md` (13 specs).

An earlier pass timestamped the same day exists at this same path but only covered 12 specs — it predates `shared-sqlite-store-spec.md` (added in commit #188, immediately before this run) and is superseded by this one. `cross-spec-contracts.md` was read as the existing frozen registry (last full sweep 2026-07-14) and excluded from the reviewed set; contradictions with it are treated as HIGH per this run's severity convention, same as the prior pass. All findings below were checked against the actual spec text (grepped line numbers, not just the extraction pass's paraphrase) before being written up — see inline quotes.

## Contradiction matrix

- **GAP-1 — Verdict's `stale_feed` gate, claimed live by two other sources, still doesn't exist in `verdict-spec.md`.** Confirmed unchanged from the prior pass. `market-data-service-spec.md` and `cross-spec-contracts.md` §3 both describe an OPTIONAL `no_go_reason: 'stale_feed'` gate powered by `Mark.observed_at`. `verdict-spec.md`'s actual `no_go_reason` field (line 91) is `string | null; // 'staleness'|'drift'|'timeout'|'dedup'|'market_closed'|'breaker'|'human_rejected'` — no `'stale_feed'`, and no `getMark`/`marketData.getMark(...)` call site appears anywhere in the file despite `VerdictInput.marketData: MarketDataService` being injected and described in prose as used for "staleness/drift." **Fix:** either implement the gate (add `'stale_feed'` to the union, add a `getMark`-based staleness check using `Mark.observed_at`), or update `market-data-service-spec.md` and `cross-spec-contracts.md` §3 to stop describing it as live.

- **GAP-2 — Three specs' `mode` field is still missing `'paper'`, unchanged from the prior pass.** Confirmed via direct grep: `execution-spec.md:103` — `mode: 'live' | 'paper' | 'backtest'` — vs. `risk-manager-spec.md:88`, `verdict-spec.md:84`, `feedback-loop-spec.md:92` — all still `mode: 'live' | 'backtest'`. Risk's hard-drawdown breaker requires manual re-arm in `live` but configurable auto-re-arm in `backtest`; Verdict's HITL is bypassed in `backtest`. Neither states what `paper` does on these safety-relevant switches, even though `shared-sqlite-store-spec.md` — added in this same commit wave — confirms one physical DB file per environment (`data/samurai-{env}.sqlite`), implying `paper` is a first-class environment the store layer already anticipates while three of four consuming specs' type signatures don't. **Fix:** widen `RiskInput.mode`, `VerdictInput.mode`, `FeedbackInput.mode` to `'live' | 'paper' | 'backtest'` and state explicitly which of the two existing behaviors `paper` inherits on each (recommend: behaves like `live` for Risk's re-arm and Verdict's HITL, since paper trading is the graduation rehearsal for live discipline — user's call, see Open Questions).

- **GAP-3 — `Direction` is used as a field type across specs but is still never defined anywhere, and `debate-engine-spec.md` is still inconsistent with itself.** Confirmed unchanged. `analysts-spec.md` and `debate-engine-spec.md` both type multiple fields (`AnalystView.direction`, `DebateResult.direction`, `AnalystContribution.stance_during_debate`/`final_position`) as `Direction`, described in comments as `bullish | bearish | neutral`, but no file — including `cross-spec-contracts.md` — contains `type Direction = ...`. Worse, `debate-engine-spec.md`'s own `DebateLog.direction` hand-rolls `'bullish' | 'bearish' | 'neutral'` instead of reusing `Direction`, ~25 lines below the `DebateResult.direction: Direction` declaration in the same file. `shared-sqlite-store-spec.md`'s `debate_log` table schema also independently hand-rolls `CHECK(bullish|bearish|neutral)` rather than referencing a shared enum — a third, DB-layer instance of the same unnamed union. **Fix:** define `type Direction = 'bullish' | 'bearish' | 'neutral'` once in the shared Domain Types bucket `cross-spec-contracts.md` already uses, change `DebateLog.direction` to use it, and note in `shared-sqlite-store-spec.md` that the CHECK constraint's value set must track `Direction`.

- **GAP-4 — Dashboard's `*Row` types are still undefined, and the newly-read `shared-sqlite-store-spec.md` confirms there's no dedicated Verdict table to build `VerdictRow` from at all. Escalated to HIGH.** `dashboard-spec.md` claims "the Dashboard defines no competing shapes," but `PositionRow`, `DebateRow`, `VerdictRow`, `AnalystPerformanceRow` — the fields of `DashboardSnapshot`, the one payload this spec exists to produce — are never defined anywhere in the document. This was already flagged in the prior pass as the single biggest gap. It's now worse than "undefined field list": `dashboard-spec.md`'s `getVerdictHistory` comment says its source is `// Verdict / audit_log` (line 73), and `shared-sqlite-store-spec.md` confirms there is no dedicated Verdict/`verdict_log` table among its 13 tables at all — Verdict's only persistence surface is the Orchestrator's `audit_log` (`trace_id, stage, decision, input_digest, output_digest, timestamp`). But `audit_log.decision`/`input_digest`/`output_digest` are a compact summary string plus **hashes**, not the actual field values — `VerdictAuditEntry` (as `dashboard-spec.md` defines it) needs `.status`, `.reason`, `.hitl_override`, none of which are reconstructable from a hash. No spec anywhere states how `getVerdictHistory` is meant to read real `VerdictDecision` field values back out of `audit_log`'s digest-only rows. **Fix:** either add a `verdict_log` table (mirroring `debate_log`'s pattern) to `shared-sqlite-store-spec.md` that persists `VerdictDecision`'s actual fields, keyed by `trace_id`/`idempotency_key`, or change `audit_log.output_digest` to a queryable JSON payload for at least the Verdict stage — and only then define the four `*Row` types in `dashboard-spec.md` against a real source.

- **GAP-5 — `cross-spec-contracts.md`'s dashboard dependency list names `ClosedTrade` as a read source; `dashboard-spec.md`'s actual interface never reads it. Treated as HIGH (contradicts the frozen registry).** The registry's OPEN-GAP-B resolution text lists dashboard reads as: *"`audit_log` (Orchestrator), `OpenPosition`/`ClosedTrade` (Execution), `DebateLog` (Debate Engine), weights/attribution + `MetricsSuite` (Feedback Loop), verdict audit trail (Verdict), `getMark` (Market Data Service)."* But `dashboard-spec.md`'s `DashboardQueryStore` interface has exactly one Execution-sourced read method, `getOpenPositions(asOf): OpenPosition[]` — there is no `getClosedTrades`/`getTradeHistory` method and no `ClosedTrade` reference anywhere in the spec. Either the dashboard is missing a trade-history view the registry already promised, or the registry text is stale. **Fix:** confirm intent — if closed-trade history belongs on the dashboard (plausible for a PnL-review UI), add `getClosedTrades(limit, asOf): ClosedTrade[]` and a `TradeRow` type to `dashboard-spec.md`; if it was deliberately dropped, correct `cross-spec-contracts.md`'s dependency list.

- **GAP-6 (new) — `risk-manager-spec.md` asserts `evaluate()` is "fully deterministic given its inputs" while its own step 7 (Risk Critic) makes a real, non-deterministic LLM call in `live`/`paper` mode.** Line 77: `// Single test seam. Fully deterministic given its inputs.` immediately precedes the `RiskManager.evaluate(input): RiskDecision` interface declaration. But the Risk Critic module (added per ADR-0003, §7 of the check pipeline, line 134) states: *"In `live`/paper mode, the critic makes a real LLM call."* The spec does reconcile this for **backtest** ("replay-from-log, not a live call"), but the top-of-file purity claim is unqualified and now stale relative to the Risk Critic module added later in the same document. **Fix:** qualify the interface comment, e.g. `// Deterministic in backtest (critic replays from log); in live/paper the critic step makes a real LLM call.`

## Security findings

**HIGH** — `risk-manager-spec.md`: unchanged from the prior pass — no spec states what `evaluate()` does if `PortfolioView`, `BreakerState`, or `MarketDataService.getMark`/`getIndicator` reads fail, time out, or return stale data, despite this spec billing itself as "the stage that must be trusted absolutely under stress." The Risk Critic module explicitly defers its own fail-open/fail-closed question ("Not yet decided — deferred to implementation tickets"), but that's scoped to the critic call only; the mechanical steps' upstream-read failure mode is unaddressed entirely. **Fix:** state explicitly that `evaluate()` fails closed (rejects the intent) on any required upstream read failure or staleness beyond a stated bound.

**HIGH** — `risk-manager-spec.md` + `shared-sqlite-store-spec.md`: confirmed and strengthened this pass. `BreakerState` is consumed as an opaque `evaluate()` input (`RiskInput.breakers: BreakerState`, line ~88) with no field list given anywhere in `risk-manager-spec.md`, and `evaluate()` is described as a pure, deterministic function — meaning nothing in the file writes a breaker trip/reset transition. This pass directly confirms the persistence side is also missing: grepping `shared-sqlite-store-spec.md` — the document that just consolidated all 13 other tables including newly-added ones like `dial_adjustments` and `cosine_setups` — for "breaker" or "circuit" returns **zero matches**. The consolidation pass that closed every other spec's storage gap (per its own commit history, e.g. fixing `latest_mark.asset_class` per #183, flagging FL's `config_trials` read-only boundary per #185) did not add a breaker-state table, which means the gap survived a dedicated schema-consolidation effort. **Fix:** add a `breaker_state` table to `shared-sqlite-store-spec.md` (tier + armed/tripped + peak values + timestamps) and name its writer in `risk-manager-spec.md` — either `RiskDecision.next_breaker_state: BreakerState` as an explicit output field, or a separate breaker-monitor component.

**MEDIUM** — `verdict-spec.md` + `feedback-loop-spec.md`: unchanged — the Telegram/Discord `ApprovalChannel` gates both live-money HITL approval (Verdict) and risk-threshold-loosening approval (Feedback Loop), and neither spec — nor any other read this pass — defines who can approve/reject, whether the callback is authenticated, or whether the channel itself is access-controlled. `verdict-spec.md` doesn't even give `ApprovalChannel` a method signature (no interface block at all, unlike every other collaborator type in that file). **Fix:** define authn/integrity requirements and a minimal interface (`request()`/`respond()`) for `ApprovalChannel` in whichever spec ends up owning notifications infra (currently unowned).

**MEDIUM** — `analysts-spec.md`, `debate-engine-spec.md`, `market-intelligence-spec.md`: unchanged, independently reconfirmed in all three this pass — analyst free text (`key_points`, `rationale`) and raw social/news text (Grok's Twitter/Reddit/Telegram/Discord ingestion, explicitly named as LLM input in `market-intelligence-spec.md`) flow through multiple LLM calls with zero mention of prompt-injection defenses, despite explicitly ingesting adversarial-content-prone public social media. **Fix:** document as an accepted risk with a stated mitigation posture — e.g. confirm mechanical downstream stages (Trader) only ever consume structured `Direction`/`confidence` fields, never free text.

**LOW** — `dashboard-spec.md`: unchanged — LAN-opt-in mode (`HOST` env var) has no authentication and the spec doesn't confirm HTML-escaping discipline for rendered free-text fields (debate rationale, verdict reasons). **Fix:** state the escaping requirement and acceptable `HOST` values explicitly.

**Confirmed clean** — Idempotent order IDs (`hash(instrument + bar/timestamp)`, Trader-assigned, deliberately not `debate_id`) are described identically in `trader-spec.md`, `execution-spec.md`, `shared-sqlite-store-spec.md`'s `open_positions`/`fills`/`closed_trades` PKs, and `cross-spec-contracts.md` §7 — verified consistent across all four this pass, no drift. `execution-spec.md`'s two-layer dedup and partial-fill handling (`filled_size` vs `requested_size`) remain well-specified and match `shared-sqlite-store-spec.md`'s schema exactly, including the `Fill.cost_breakdown` optional-field pattern from the earlier GAP-F fix. `cost-model-backtest-spec.md`'s no-lookahead audit remains explicitly fail-closed. `market-data-service-spec.md`'s point-in-time/no-lookahead/survivorship-free guarantees are the strongest-specified compliance section read this pass, each backed by a named test.

## Design-practice findings

**MEDIUM** — `trader-spec.md` + `verdict-spec.md` + `shared-sqlite-store-spec.md`: `PositionStore`/`positionState` is referenced by that exact name in `trader-spec.md` and `verdict-spec.md` but no spec defines an interface literally named `PositionStore`. `shared-sqlite-store-spec.md` confirms Execution's `open_positions` table is the actual backing store, and `execution-spec.md` only ever calls it `SharedStore`, not `PositionStore`. This is a naming-only gap (the data model is otherwise consistent — same idempotency-key PK, same fields), but every consuming spec should reference the same name. **Fix:** name Execution as owner and either rename all `PositionStore`/`positionState` references to match `SharedStore`, or add a typed `PositionStore` accessor interface backed by `open_positions`.

**MEDIUM** — `dashboard-spec.md` + `feedback-loop-spec.md` + `shared-sqlite-store-spec.md`: unchanged and now directly confirmed by the schema — `dashboard-spec.md`'s `getDailyMetrics` carries the comment `// Feedback Loop (cost-model-owned computation)`, `feedback-loop-spec.md` says `MetricsSuite` is recomposed not reimplemented, and `shared-sqlite-store-spec.md`'s 13-table list confirms there is genuinely **no** table anywhere that persists a queryable daily `MetricsSuite` row — the closest thing is `config_trials.result_json`, a JSON blob of a full `BacktestReport`, not a per-day metrics row keyed for dashboard reads. **Fix:** add a `daily_metrics` table (or equivalent) to `shared-sqlite-store-spec.md`, name its writer (Feedback Loop, per its own "recomposes" framing) explicitly.

**MEDIUM (new)** — `risk-manager-spec.md`: step 6 (concentration check) was corrected mid-spec-lifecycle (per #186, dated 2026-07-26 — the same day as this pass) from "static v1 buckets" to a dynamic pairwise Pearson correlation matrix over trailing returns, computed in `evaluate()`'s synchronous hot path before every order. No caching or recompute-frequency strategy is stated — is the correlation matrix recomputed from scratch on every gated intent, or cached/refreshed periodically? Given `evaluate()` already picks up a real LLM call in step 7 (live mode), an uncached O(n²) correlation recompute on every intent compounds an already-unbudgeted latency path (see Performance findings). **Fix:** state a caching/recompute-cadence decision for the correlation matrix, even if "recompute per tick, cache within a tick" is the answer.

**MEDIUM (new)** — `market-intelligence-spec.md` + `risk-manager-spec.md`: unchanged — both specs assert WorldMonitor's CII score reaches Risk Manager via a named-but-undefined path. `risk-manager-spec.md` cites "`cii-consumer.ts` (ADR-0002)"; `market-intelligence-spec.md` names the same file (`src/market-intelligence/worldmonitor-adapter/cii-consumer.ts`) but states only that it will "separately pull CII scores and emit them to the Risk Manager," with no method signature, push/pull mechanism, or cadence defined in either file. **Fix:** pick an owner (Market Intelligence, since it names the file) and define the actual call/subscription Risk Manager makes.

**MEDIUM (new)** — `orchestrator-spec.md`: mid-pipeline crash recovery is asymmetric and the asymmetry isn't called out. `current_tick` survives a crash only as a disposable progress indicator; if a crash happens after Verdict returns `go` but before `Execution.execute` is ever called, nothing resumes that specific tick — the order is simply never placed, and nothing in `orchestrator-spec.md` or `execution-spec.md` alerts on a `go`-verdict-with-no-matching-execution-attempt. Given the project's dead-man's-switch/heartbeat design already covers "the system is down," this is the narrower and arguably more dangerous case of "the system silently dropped one decided trade while staying up." **Fix:** either have the Orchestrator re-check `audit_log` for orphaned `go` verdicts with no matching `execution_result` on restart and retry/alert, or explicitly document this as an accepted risk.

**LOW** — `debate-engine-spec.md`: unchanged — `DebateLog.rounds` and `DebateResult.rounds_completed` name the identical concept differently on two sibling types in the same file. **Fix:** rename one to match the other.

**LOW** — `analysts-spec.md`: unchanged — `AnalystRunResult.analyst_count`'s "before failures" semantics are one cross-reference away from misreading; not an active contradiction. **Fix:** tighten the wording locally.

## Performance / maintainability / complexity / simplicity findings

**MEDIUM** — `market-data-service-spec.md`: unchanged — recursive indicators (EMA/RSI/ATR) with pinned lookback warm-up have no stated incremental-computation strategy; the Tier-1 cache only helps within a single `asOf`, not across ticks where the value legitimately changes every bar close. **Fix:** state a decision (even "full recompute is fine at MVP scale") explicitly.

**LOW** — `orchestrator-spec.md` + `shared-sqlite-store-spec.md`: `audit_log` retention/pruning is unaddressed in both the table's original owning spec and the newly-consolidated schema spec — confirmed absent in both this pass. `shared-sqlite-store-spec.md`'s Out-of-Scope section does contrast a *different* store's 90-day auto-purge with "this store's permanent-retention requirement — CLAUDE.md: track everything for HMRC/CGT," which implies the intended policy is "never purge," but that's stated only by contrast, never as an explicit line item for `audit_log` itself — and `audit_log` has only one index (`trace_id`), no index on `timestamp`, so a future "audit log for the last N days" dashboard query has nothing to range-scan on. **Fix:** state the permanent-retention decision explicitly against `audit_log` by name, and add a `timestamp` index if date-range dashboard queries are ever expected.

**LOW** — `debate-engine-spec.md`: unchanged — the latency-budget arithmetic doesn't self-consistently support its own stated hard caps (crypto: "~15-17s total" against a 15s cap; stocks: "~60-65s total" against a 60s cap). Acknowledged as rough estimates to tune in Stage 1.

## Confirmed clean

- Fractional-Kelly sizing discipline in `trader-spec.md` is explicit, correctly cites the research constraint ("never full Kelly... research: full Kelly implies 50-80% drawdowns"), and the caps-ownership boundary against `risk-manager-spec.md` (Trader enforces per-trade cap only; Risk enforces portfolio/asset-class caps and breakers) is stated identically on both sides with no overlap or gap.
- `Direction` mapping to order side (`bullish→buy`, `bearish→sell`, `neutral→no entry`) is identical, verbatim-matching text in `trader-spec.md` and `debate-engine-spec.md` — no drift, independent of the `Direction`-type-definition gap noted in GAP-3.
- `shared-sqlite-store-spec.md`'s per-table ownership (one owning spec per table, no shared/catch-all tables) is consistently honored across all 13 tables checked against their respective owning specs this pass — `bars`/`latest_mark` (MDS), `open_positions`/`fills`/`closed_trades` (Execution), `config_trials` (cost-model), `analyst_weights`/`strategy_params`/`risk_thresholds`/`dial_adjustments`/`cosine_setups` (Feedback Loop), `debate_log` (Debate Engine), `audit_log`/`current_tick` (Orchestrator) — every field referenced by a consuming spec traces back to a table defined here with matching semantics.
- No-lookahead/point-in-time enforcement is independently and consistently implemented at three different layers with matching framing (`close_time <= asOf` in MDS, `timestamp <= clock.now()` cursor boundary in Market Intelligence's replay, injected-clock pattern in Analysts/Trader/Risk/Verdict/Orchestrator) — all describe the same invariant without contradicting each other on where enforcement lives.

## Open questions

1. **What should `mode: 'paper'` actually do on Risk's hard-breaker re-arm and Verdict's HITL bypass?** (GAP-2) This is the graduation-gate stage per CLAUDE.md ("backtest → paper → tiny live capital") — recommend both behave like `live` (manual re-arm, HITL required) since paper trading exists specifically to rehearse live discipline, but this is a deliberate safety-posture call, not a naming fix.
2. **Does the Dashboard need closed-trade history?** (GAP-5) `cross-spec-contracts.md` says yes (lists `ClosedTrade` as a read dependency); `dashboard-spec.md`'s actual interface says no. If yes, it needs a new method + `TradeRow` type; if no, the registry needs correcting.
3. **Where does Verdict's audit history actually live?** (GAP-4) `audit_log` stores digests/hashes, not full field values, so `getVerdictHistory` currently has no data source that can return real `VerdictAuditEntry.reason`/`.hitl_override` values. This wants a decision on whether it's a new `verdict_log` table or a richer `audit_log.output_digest`.
