# Cross-Spec Verification Pass — 2026-07-26

Specs reviewed (folder: `docs/specs/`): `analysts-spec.md`, `cost-model-backtest-spec.md`, `dashboard-spec.md`, `debate-engine-spec.md`, `execution-spec.md`, `feedback-loop-spec.md`, `market-data-service-spec.md`, `market-intelligence-spec.md`, `orchestrator-spec.md`, `risk-manager-spec.md`, `trader-spec.md`, `verdict-spec.md` (12 specs).

`cross-spec-contracts.md` was read as the existing frozen registry (last full sweep 2026-07-14) and excluded from the reviewed set. Contradictions with it are treated as HIGH per this run's severity convention. All findings below were verified against the actual spec text (not just the extraction pass's paraphrase) before being written up.

## Contradiction matrix

- **GAP-1 — Verdict's `stale_feed` gate, claimed live by two other sources, doesn't exist in `verdict-spec.md`.** `market-data-service-spec.md` states as a "Cross-spec requirement": *"`Mark.observed_at` enables an OPTIONAL new Verdict feed-staleness no-go (`no_go_reason: 'stale_feed'`) that supplements — does not replace — Verdict's existing `decision_timestamp` signal-age gate."* `cross-spec-contracts.md` §3 repeats this as an already-settled addition: *"Powers Verdict's OPTIONAL `no_go_reason: 'stale_feed'` gate (supplements, does not replace, `decision_timestamp` signal-age gate)."* But `verdict-spec.md`'s actual `no_go_reason` union is `'staleness'|'drift'|'timeout'|'dedup'|'market_closed'|'breaker'|'human_rejected'` — no `'stale_feed'` value anywhere, and Verdict's staleness gate is entirely `decision_timestamp`-based; there is no `getMark`/`Mark.observed_at` call anywhere in the file, even though `VerdictInput.marketData: MarketDataService` is injected. Two independent sources (a sibling spec and the frozen registry) describe a gate that was never actually built into the consuming spec. **Fix:** either implement the gate in `verdict-spec.md` (add `'stale_feed'` to the union, add a `getMark`-based check), or — if it was deliberately dropped — update `market-data-service-spec.md` and `cross-spec-contracts.md` §3 to stop describing it as live, since as written they'll mislead an implementer into assuming Verdict already gates on feed staleness.

- **GAP-2 — Three specs' `mode` field is missing the `'paper'` value that a fourth spec's mode matrix treats as materially distinct.** `execution-spec.md` defines `ExecutionInput.mode: 'live' | 'paper' | 'backtest'`, and `cost-model-backtest-spec.md`'s mode matrix explicitly treats `paper` as a third regime (shares live clock/data with `live`, shares the simulated cost model with `backtest` — not an alias for either). But `risk-manager-spec.md` (`RiskInput.mode: 'live' | 'backtest'; // selects manual vs auto re-arm for the hard breaker`), `verdict-spec.md` (`VerdictInput.mode: 'live' | 'backtest'; // backtest bypasses HITL`), and `feedback-loop-spec.md` (`FeedbackInput.mode: 'live' | 'backtest'`) all only have two values. This isn't cosmetic: Risk's hard-drawdown breaker requires *manual* re-arm in `live` but a *configurable auto* re-arm in `backtest` — which applies during paper trading, where a hard-drawdown trip is a meaningful signal but the capital isn't real? Verdict's HITL bypass is explicitly a `backtest`-only behavior — does paper trading also bypass human approval, or not? Paper trading is this project's own graduation gate before real money (CLAUDE.md: "backtest → paper → tiny live capital"), so leaving its behavior on these three safety-relevant switches undefined is a real gap, not a formality. **Fix:** widen `RiskInput.mode`, `VerdictInput.mode`, and `FeedbackInput.mode` to `'live' | 'paper' | 'backtest'`, and state explicitly which of the two existing behaviors `paper` inherits on each (recommend: paper behaves like `live` for Risk's re-arm and Verdict's HITL, since it's real-time and the whole point of the graduation gate is rehearsing live discipline — but this is the user's call, see Open Questions).

- **GAP-3 — `Direction` is used as a field type across specs but is never defined anywhere, and the one spec that uses it most doesn't even use it consistently with itself.** `analysts-spec.md` (`AnalystView.direction: Direction`) and `debate-engine-spec.md` (`AnalystView.direction`, `DebateResult.direction`, `AnalystContribution.final_position`, all typed `Direction`) all reference a `Direction` type — comments describe it as `bullish | bearish | neutral`, but no file in this 12-spec set contains a `type Direction = ...` declaration. This is the literal type `trader-spec.md` maps straight to order side (`bullish→buy`, `bearish→sell`), so it's load-bearing, not incidental. Worse, `debate-engine-spec.md`'s own `DebateLog.direction` (same file, ~25 lines below its `DebateResult.direction: Direction` declaration) is typed as a hand-written literal union `'bullish' | 'bearish' | 'neutral'` instead of `Direction` — meaning the spec that most relies on this type doesn't consistently use its own reference to it. **Fix:** define `type Direction = 'bullish' | 'bearish' | 'neutral'` once, in the shared Domain Types & Contracts bucket that `market-data-service-spec.md` and `cross-spec-contracts.md` already use for cross-cutting types, and change `DebateLog.direction` to use `Direction` instead of a separately hand-rolled union.

- **GAP-4 — Dashboard's own output payload types are never defined, contradicting its explicit "we define no competing shapes" claim.** `dashboard-spec.md` states: *"`OpenPosition`, `DebateLog`, `Mark`, `MetricsSuite` reuse the exact types already defined in execution-spec.md, debate-engine-spec.md, market-data-service-spec.md, and cost-model-backtest-spec.md respectively... the Dashboard defines no competing shapes."* That claim only covers the four types it reads from stores. But `DashboardSnapshot` (the thing `buildSnapshot` actually returns, and the one wire payload this spec is entirely about) is built from `positions: PositionRow[]`, `debates: DebateRow[]`, `verdicts: VerdictRow[]`, `analysts: AnalystPerformanceRow[]` — and none of these four row types has a field defined anywhere in this spec or any other. There's no stated mapping from `OpenPosition`/`DebateLog`/`VerdictAuditEntry`/weights+attribution to these row shapes (1:1 alias? a narrower projection? new fields entirely?). This is the single biggest gap in the pass — an implementer has no contract for the type the whole spec exists to produce. **Fix:** define each `*Row` type explicitly in `dashboard-spec.md` before `/to-tickets`, even if each is just `type PositionRow = Pick<OpenPosition, ...> & { unrealized_pnl: number }`-style aliases plus the fields User Story 1 lists in prose.

## Security findings

**HIGH** — `risk-manager-spec.md`: no spec defines what `RiskManager.evaluate()` does if `PortfolioView`, `BreakerState`, or `MarketDataService.getMark`/`getIndicator` reads fail, time out, or return stale data — despite this spec explicitly billing itself as "the stage that must be trusted absolutely under stress." **Fix:** state explicitly that `evaluate()` fails closed (rejects the order intent) on any required upstream read failure or staleness beyond a stated bound.

**HIGH** — `risk-manager-spec.md`: `BreakerState` is consumed as an opaque input to `evaluate()`, and the spec discusses trip/reset semantics at length, but no field, return value, or named module anywhere (not in this spec, not in Execution, Feedback Loop, or Orchestrator) owns *persisting* a breaker trip or reset. `evaluate()` is stated to be a pure function of its inputs — meaning nothing in the reviewed specs actually writes the state transition the whole circuit-breaker design depends on. An un-persisted trip means the hard-drawdown breaker doesn't protect anything past the first call. **Fix:** add `RiskDecision.next_breaker_state: BreakerState` as an output field, or name an explicit owner for the breaker-state-mutation write path.

**MEDIUM** — `verdict-spec.md` + `feedback-loop-spec.md`: the Telegram/Discord `ApprovalChannel` gates both the live-money HITL approval in Verdict (the last check before an order is placed) and the risk-threshold-loosening approval in Feedback Loop, but no spec anywhere defines who can approve/reject, whether the callback is authenticated or signed, or whether the channel itself is access-controlled. This is the human safety gate immediately before real capital moves. **Fix:** define authn/integrity requirements for `ApprovalChannel` in whichever spec ends up owning notifications infrastructure (currently unowned by any of the 12).

**MEDIUM** — `analysts-spec.md`, `debate-engine-spec.md`, `market-intelligence-spec.md` (same gap, independently confirmed in all three): analyst free text (`key_points`, `rationale`) and raw social/news text flow through multiple LLM calls (per-analyst, then up to 3 rounds of bull/bear/mediator debate) with zero mention of prompt-injection defenses anywhere, despite explicitly ingesting public social media as a source — a plausible adversarial-content vector (e.g. coordinated pump-and-dump posts engineered to influence the debate LLM). **Fix:** at minimum, document this as an accepted risk with a stated mitigation posture — e.g. confirm that mechanical downstream stages (Trader) only ever consume the structured `Direction`/`confidence` fields, never free text, which already contains the blast radius; state that explicitly rather than leaving it unaddressed in three specs.

**LOW** — `dashboard-spec.md`: the LAN-opt-in mode has no authentication and no mention of HTML-escaping for free-text fields (debate rationale, analyst reasoning) rendered into the single-page HTML app — a plausible stored-XSS surface if that content is ever templated into innerHTML unescaped. Also no validation ruling out a `HOST=0.0.0.0` misconfiguration binding all interfaces rather than just the LAN. **Fix:** add an explicit HTML-escaping requirement for rendered free-text fields, and a one-line note on acceptable `HOST` values.

**Confirmed clean** — Idempotent order IDs (`hash(instrument + bar/timestamp)`, Trader-assigned, deliberately not `debate_id`) are described identically in `trader-spec.md`, `execution-spec.md`, and `cross-spec-contracts.md` §7 — no drift found. `execution-spec.md`'s two-layer dedup (local store + broker client-order-id) and partial-fill handling are both well-specified and internally consistent. `cost-model-backtest-spec.md`'s no-lookahead audit is explicitly fail-closed ("a failed lookahead check fails the run, it does not warn").

## Design-practice findings

**MEDIUM** — `trader-spec.md` + `verdict-spec.md`: both inject a `PositionStore` (`positionState`/`positionStore`) but no spec — not Execution (which owns `OpenPosition`/`Fill`/`ClosedTrade` but never names a `PositionStore` interface), not Risk (whose portfolio-accounting module reads "the shared SQLite store" generically) — defines this type or names an owner. **Fix:** name Execution as the owner (it already owns positions) and define at minimum the lookup-by-idempotency-key method both Trader and Verdict need.

**MEDIUM** — `dashboard-spec.md` + `feedback-loop-spec.md`: `dashboard-spec.md`'s `getDailyMetrics(asOf): MetricsSuite` store method carries the inline comment `// Feedback Loop (cost-model-owned computation)`, attributing the query's origin to Feedback Loop, while `feedback-loop-spec.md` itself states `MetricsSuite` is *"OWNED by the cost-model/backtest validation library... FL RECOMPOSES — it does not reimplement the math."* Neither spec states which component actually persists a queryable `MetricsSuite` row for the dashboard to read; FL's `MetricsReport.daily` is described as a recomposition into FL's own return type, not necessarily a written table. **Fix:** name which spec's persistence layer writes the row `getDailyMetrics` reads.

**MEDIUM** — `market-intelligence-spec.md` + `risk-manager-spec.md`: both specs assert the same relationship (WorldMonitor's CII score reaches Risk Manager, bypassing the normal `MarketContext` path) but neither defines the actual interface — push or pull, method signature, cadence. `risk-manager-spec.md` names an adapter file (`cii-consumer.ts`) that `market-intelligence-spec.md` never mentions. **Fix:** pick an owner (Market Intelligence, since it names the file) and define the call Risk Manager actually makes or is called by.

**LOW** — `debate-engine-spec.md`: `DebateLog.rounds` and `DebateResult.rounds_completed` name the identical concept ("actual rounds run") differently on two sibling types in the same file. **Fix:** rename one to match the other (recommend `rounds_completed` on both).

**LOW** — `analysts-spec.md`: `AnalystRunResult.analyst_count` is commented "before failures," and the Debate Engine quorum-math prose nearby could be misread as a post-failure count by a reader who doesn't carry both comments in mind at once — the worked examples (1-of-2=50%, 2-of-3=67%) are internally consistent, so this isn't an active contradiction, but it's one accidental off-by-one away from becoming one. **Fix:** tighten the wording so `analyst_count`'s "before failures" meaning is unambiguous without cross-referencing a different section.

## Performance / maintainability / complexity / simplicity findings

**MEDIUM** — `market-data-service-spec.md`: recursive indicators (EMA/RSI/ATR) requiring pinned lookback warm-up have no stated incremental-computation strategy — if implemented as full-window recompute per tick rather than incrementally advanced state, this is a real slow-at-scale risk given the service is "queried by 4 different consumers per tick" across a full backtest replay (thousands of ticks × multiple instruments × multiple indicators). **Fix:** state a decision on incremental vs. full-recompute, even if "full recompute is fine at MVP scale" is the answer — make it a stated decision, not a silent gap.

**LOW** — `orchestrator-spec.md`: `audit_log` has no retention/archival/pruning policy despite being written to on every stage decision for every instrument on every tick, 24/7 for crypto. Not a blocker at MVP scale but worth a stated decision before it becomes an unbounded table.

**LOW** — `debate-engine-spec.md`: the latency-budget arithmetic doesn't self-consistently support its own stated hard caps (crypto: "~2s per analyst (6-8s) + ~3s per round × 3 rounds (9s) = ~15-17s total" against a stated 15s cap; stocks: "~60-65s total" against a 60s cap) — the spec's own upper-bound estimates exceed the caps they're meant to justify. Acknowledged as rough estimates to tune in Stage 1, so cosmetic, not load-bearing.

**Confirmed clean** — Both `risk-manager-spec.md` and `cost-model-backtest-spec.md` show good proportionality to stated scale and good deferred-complexity judgment (static correlation buckets deferred to v2, CII sizing deferred pending real data, order-book-level impact model explicitly deferred) — no overengineering found in either. `feedback-loop-spec.md`'s daily-batch (not online/real-time) weight-tuning cadence is a well-justified simplicity choice over a fully online learner. `execution-spec.md`'s "one code path, only the adapter differs" principle across live/paper/backtest is a strong simplicity win, consistent across every spec that injects `Clock`/`MarketDataService`.

## Open questions

This changes real operator experience during the paper-trading graduation gate and needs a decision, not just a type widening.
- **GAP-1 follow-up:** was the `stale_feed` gate deliberately dropped when `verdict-spec.md` was last written, or simply missed? If deliberate, `market-data-service-spec.md` and `cross-spec-contracts.md` §3 need updating so they stop describing it as already-decided.
- **GAP-4 follow-up:** should the dashboard's `*Row` types be pure aliases of the upstream types (simplest, but may leak internal fields the UI doesn't need) or explicit narrower projections (more work, cleaner UI contract)? This is a real design choice, not just a documentation gap.
