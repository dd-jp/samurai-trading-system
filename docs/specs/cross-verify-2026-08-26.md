## Design-practice findings

**Confirmed clean, not a gap:** the addition has the Universe Selector call Alpha Vantage directly rather than routing through `MarketDataService`. This looked like a candidate contradiction going in — registry §3 names `MarketDataService` as the interface for Analysts/Trader/Risk/Verdict — but `universe-selector-spec.md`'s existing "Market data — Alpaca free Basic..." section already establishes that the screener **constructs its own HTTP client and bypasses MDS entirely**, because MDS is "strictly single-symbol" and the screener needs batched, out-of-session, SIP-pinned reads MDS doesn't serve. The earnings-day filter's direct Alpha Vantage call follows the identical, already-accepted pattern (a second out-of-session, screener-time-only vendor call) rather than introducing a new one.

**MEDIUM — GAP-L: an unverified ownership claim, caught and fixed during this pass, not left in the spec.** The subsection's original text asserted "an earnings release on a name already held is a Risk Manager concern (position management), not a Universe Selector one" — implying `risk-manager-spec.md` already owns held-position earnings handling. It does not: `grep -n -i "earnings\|position_check" docs/specs/risk-manager-spec.md` returns zero matches. This was an unverified delegation, the exact "silent assumption" pattern this skill exists to catch (registry's own history has one precedent: `DebateLog` went unspecced the same way until a verification pass caught it). **Fix, already applied:** the subsection now states this is an explicit scope boundary — entry-day exclusion only, per #926's actual question — and names held-position earnings exposure as an unaddressed gap rather than an implicit Risk Manager responsibility. No spec file claims ownership of it; it is not tracked as a new registry entry because #926 never asked for it and inventing scope here would be adding an untracked feature during a verification pass, not fixing one.

No missing idempotency, no missing error-boundary gap: the filter is a pure exclusion applied once per day inside an already-idempotent daily run (the screener's own completed-bars-only, re-run-produces-same-output invariant, `universe-selector-spec.md` "Completed bars only"), and a failed Alpha Vantage call degrades to "exclusion list empty for today" rather than blocking the screener — consistent with the existing pool `fallback_default` design philosophy of never letting one data source's failure dark the whole session. (This degrade-on-failure behavior is implied by the addition's existing "Residual risk" paragraph on reschedule staleness but is not spelled out as an explicit failure-mode contract; noted below as a LOW open item, not elevated to MEDIUM since the existing "Failure modes, specified rather than discovered" module in the same spec already establishes the pattern this would follow.)

## Open questions

## Addendum — 2026-08-27, second pass

A follow-up review of this pass itself (before #928 was marked `ready-for-agent`) found four further issues, all fixed on the spec/ticket rather than left as open questions:

- **HIGH — the vendor-eligibility claim was under-verified.** `docs/research/39`'s live evidence is a call against Alpha Vantage's public `apikey=demo` key, which proves the endpoint returns forward-dated rows for *some* caller, not that a real, registered free-tier key can call `EARNINGS_CALENDAR` at all — AV serves demo payloads for some premium-only functions too, and doc 39's own text already hedges this ("no fetched page states that `EARNINGS_CALENDAR` is live for `demo` specifically"), but the first cross-verify pass didn't act on that hedge. **Fix:** `ready-for-agent` removed from #928; a blocker section and a first-position AC bullet require one real-key test call before implementation starts, with an explicit fallback to Finnhub if it 403s.
- **MEDIUM — pool-size interaction with the exclusion was unaddressed.** The checked-in pool (32 rows / 26 distinct `screening_instrument`, 20 single-stock and exclusion-eligible) can shrink well below the static ~25-row line the "Candidate pool" section sizes its ranking mechanism against, since US large-caps cluster earnings into ~3-week windows and several single-stock rows can be excluded simultaneously. That static check was a first-commit sizing decision, not a runtime floor, and nothing said so. **Fix:** new "Pool-size interaction" paragraph added to the spec subsection and a matching AC/scope note added to #928, stating ranking must not be skipped or short-circuited on a shrunk-but-nonzero pool.
- **LOW — "reuse #685's corrected rule directly" overstated the fidelity.** #685's rule is a three-way time test (pre-09:30 / 09:30–16:00 intraday / post-16:00 ET); Alpha Vantage's `timeOfTheDay` carries no release timestamp, only a two-bucket-plus-blank classification, so the intraday branch can't be evaluated and collapses into the blank/exclude case by construction. The filter's exclusion behavior is unchanged (still conservative), but a future reader comparing the live filter against #685's measurement would wrongly assume identical classifiers. **Fix:** spec and #928 reworded to state the coarsening explicitly.
- **LOW — the exclusion's date resolution didn't restate the shared-calendar hazard.** The same spec already carries a standing warning ([#696](../../issues/696): the US equity calendar is weekend-only, e.g. trades through Thanksgiving if derived locally) for the cadence/session-boundary logic a few sections down, but the new subsection's "prior trading day" / "session being built" resolution didn't repeat it. **Fix:** added to both the spec subsection and #928's AC.

No new HIGH contradiction with another spec or the frozen registry was found in this second pass; all four items are corrections within the addition itself, not new cross-spec conflicts.
