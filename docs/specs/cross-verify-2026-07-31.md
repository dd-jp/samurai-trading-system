## Contradiction matrix

- **GAP-7 (HIGH, FIXED IN THIS PASS) — `peak_equity`'s proposed persistence home was documented as disposable state that gets deleted every tick, but `peak_equity` must be a durable, monotonic, crash-surviving high-water mark.** transport-layer-spec.md's AccountStateProvider module said: *"`peak_equity` — a small new locally-persisted running max of equity, updated once per tick... Natural home: the existing shared SQLite store, alongside `SqliteCurrentTickStore`'s table."* But shared-sqlite-store-spec.md's `current_tick` table is explicitly documented as *"Disposable, best-effort progress state — NOT a system-of-record... deleted on tick completion."* A value stored "alongside" a table with a delete-on-completion lifecycle would either get wiped every tick (silently disabling the hard portfolio-drawdown circuit breaker `peak_equity` feeds) or need a schema `current_tick`'s documented lifecycle contradicts. **Fixed in this pass:** transport-layer-spec.md's `peak_equity` module now specifies a new, genuinely durable table; shared-sqlite-store-spec.md gained the matching `account_state(key TEXT PRIMARY KEY, peak_equity REAL NOT NULL, updated_at TEXT NOT NULL)` DDL (single upserted row, never deleted), table count updated 17→18, Non-Collision Verification and pipeline-integration diagram updated to match.

- **GAP-8 (HIGH, needs David's decision — not resolved by this pass) — `AccountStateProvider.daily_pnl_pct` may be a single blended scalar sourced from a stock-market-day boundary, while risk-manager-spec.md's `PortfolioView.daily_pnl_pct` calls for asset-class-specific session boundaries that don't exist for a 24/7 asset.** risk-manager-spec.md defines: *"`PortfolioView.daily_pnl_pct: number` — since session start (UTC day crypto / market-day stocks)."* transport-layer-spec.md's AccountStateProvider sources it from Alpaca's `GET /v2/account` (`equity`/`last_equity`) — a single combined brokerage response covering both asset classes (ADR-0001). **The factual premise needs verification, not just the decision:** whether Alpaca's `last_equity` is actually scoped to the stock market's trading-day boundary (as its field name and Alpaca's public docs suggest) is *unverified* — #260's original research had no live network access to confirm this empirically against a real account. If it is stock-calendar-scoped, the crypto side of a mixed portfolio gets a number that doesn't match risk-manager-spec.md's stated UTC-day semantics; if Alpaca's semantics turn out to already be timezone/calendar-neutral, this gap may not exist at all. transport-layer-spec.md has been edited this pass to flag this as an explicit open decision (not a silent default) rather than stating `last_equity`'s semantics as settled fact. **This is a genuine product/risk decision for David, not something to guess:** (a) accept the single Alpaca-sourced blended figure once its actual semantics are confirmed (relaxing risk-manager-spec.md's stated UTC-day requirement to match reality), or (b) build a locally-persisted UTC-midnight equity snapshot for a true crypto-scoped figure (same new `account_state` table GAP-7 added, extended with a `daily_open_equity`/`daily_open_at` column pair). Needs sign-off before `/implement`.

## Performance / maintainability / complexity / simplicity findings

**MEDIUM:**
- **transport-layer-spec.md's reactive-only rate-limit handling (backoff-on-429) has no proactive throttle for Polygon's 5-calls/min free tier**, which is nearly 40x tighter than Alpaca's ~200/min. Stage 2's batch ingestion (multiple symbols × multi-year date ranges, per stage2-validation-execution-spec.md) will trigger 429s routinely under a reactive-only policy rather than pacing calls to stay under the limit. Not blocking (retry-after-429 will eventually succeed, just slowly), but a token-bucket/leaky-bucket proactive limiter would be a meaningfully better fit for Stage 2's batch shape than exponential backoff alone. Flagged in transport-layer-spec.md's Out of Scope as "exact retry config numbers... an implementation/tuning detail" — this finding is one level up from config tuning: the *mechanism* (reactive vs proactive) is the gap, not just the numbers.

**LOW:**
- Carried forward from 2026-07-28, still true: risk-manager-spec.md's Risk Critic LLM round-trip plus the new O(n²) correlation-matrix check together grow the Risk stage's latency budget without a restated total; shared-sqlite-store-spec.md's single-file write-contention risk remains correctly deferred to Future Extensions.
