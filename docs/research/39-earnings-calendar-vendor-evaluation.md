# Earnings-calendar vendor evaluation — the per-instrument entry filter's data source

**Status:** RESEARCHED 2026-08-26. Resolves Open Question 2 of [wayfinder map #926](https://github.com/dd-jp/samurai-trading-system/issues/926) ("single-name earnings-day entry filter — placement and data source"), which named a live earnings-calendar vendor API as the option to evaluate against the checked-in-list alternative and flagged the choice to David directly. Everything below is read from each vendor's own current documentation/terms, fetched live this session — not from training-data recall, which is stale on at least one of these vendors (Polygon.io rebranded to **Massive** on 2025-10-30, and its docs now live at `massive.com`, not `polygon.io`).

## Why this document exists

[#926](https://github.com/dd-jp/samurai-trading-system/issues/926) records the actual gap: the Universe Selector's once-daily 22:15 London screener (`docs/specs/universe-selector-spec.md`, "Candidate pool") has no mechanism to exclude a single-stock underlying from the next session's Watchlist when that name reports earnings around the session — even though [#685](https://github.com/dd-jp/samurai-trading-system/issues/685) measured earnings-reaction sessions at **−1.0378%/trade** (t = −2.99, 1.62% of sessions), directionally negative. ADR-0016 Decision 2 already rejected debate-wide catalyst gating; this is a narrower per-name eligibility filter, the same shape as `docs/research/17-universe-manipulation-guardrails.md`'s constraint on *which names are eligible*. The 20 single-stock underlyings in `server/providers/universe-pool/lse-etp-pool.ts` are: TSLA, NVDA, AAPL, MSFT, AMD, GOOG, PYPL, NFLX, COIN, BABA, MRNA, NIO, XYZ, AMZN, META, UBER, RACE, ARM, MSTR, PLTR.

David chose the live-vendor-API branch over a hand-maintained checked-in list. This document picks the vendor.

## What the filter needs from a vendor

1. **Forward-looking dates** — the screener runs at 22:15 London the night before the session it's building the Watchlist for; a retrospective/historical-only feed is useless here (this is exactly the gap `docs/research/18-fetch-earnings.py`'s Alpaca-News regex classifier can't fill — it labels *past* headlines after they publish).
2. **A rate limit that clears ~20 tickers once/day** — trivial in absolute terms, but free tiers vary from "per-minute" to "per-day" caps, and the per-day caps can be tight enough to matter if the vendor also serves other Samurai components later.
3. **Reschedule freshness** — companies move earnings dates; a filter built on a stale snapshot reintroduces the exact kind of look-ahead/staleness bug #685 itself had to fix (see `18-fetch-earnings.py`'s look-ahead defect, closed by #685).
4. **A licensing posture that doesn't bar automated/algorithmic trading use** — `docs/research/35-broker-venue-algo-trading-terms.md` found every Trading 212 product line prohibits "Algorithmic Trading" outright; a data vendor with an equivalent clause would be a dead end regardless of price. `docs/research/22-mi-source-licensing.md` established the frame Samurai already relies on for Alpaca News: a private, single-operator console trading one person's own capital is "personal, non-commercial" use, decided by the same read applied to every source in that document. That question is still formally **open** (`docs/research/README.md` open item 2, "Is Samurai commercial?") — this document inherits that open item rather than resolving it, same as doc 22 did for Alpaca.

## Vendors evaluated

### Alpha Vantage — `EARNINGS_CALENDAR` function — RECOMMENDED

Fetched live 2026-08-26: [`alphavantage.co/documentation/`](https://www.alphavantage.co/documentation/), [`alphavantage.co/support/`](https://www.alphavantage.co/support/) FAQ, the Terms of Service PDF at [`alphavantage.co/terms_of_service/`](https://www.alphavantage.co/terms_of_service/), and — decisively — a **live, unauthenticated call against the real endpoint** using AV's own published public demo key:

```
curl 'https://www.alphavantage.co/query?function=EARNINGS_CALENDAR&horizon=3month&apikey=demo'
```

**Forward-looking, empirically confirmed, not just asserted.** This call was made today, 2026-08-26, and returned live rows dated **today and later** — e.g. `A,AGILENT TECHNOLOGIES INCORPORATED,2026-08-26,2026-07-31,1.48,USD,post-market` and `ANF,ABERCROMBIE & FITCH COMPANY,2026-08-26,2026-07-31,1.95,USD,pre-market` — with `reportDate` values running forward from today across the whole 3-month horizon. This is the strongest possible evidence for "does the free tier actually return forward-looking dates": an unauthenticated request against the production endpoint, on the day this document was written, returning dates in the future. `symbol` is optional — omitting it returns the full market-wide list in one call, which a screener filters client-side for the 20-name pool in a single request per day. Documentation text corroborates this: the `horizon` param (`3month` default, `6month`, `12month`) is described as returning *"a list of expected company earnings in the next N months."*

**Real response schema, also confirmed by the live call, not recalled.** The actual CSV header returned is `symbol,name,reportDate,fiscalDateEnding,estimate,currency,timeOfTheDay` — one field richer than what AV's documentation page alone suggested. `timeOfTheDay` carries exactly the before/after-market timing signal #685's session-labelling logic needs (observed values in the live response: `pre-market`, `post-market`, and blank for unclassified rows) — the schema gap flagged against AV in an earlier pass of this analysis does not hold; the live data disproves it.

**Rate limit.** Support FAQ, fetched live: *"We are pleased to provide free stock API service covering the majority of our datasets for **25 API requests per day** and unlimited API requests for verified open-source or educational projects."* This filter needs **one call/day** (the unfiltered `horizon` query, filtered client-side to the 20-name pool) — 4% of the daily cap. The concern in an earlier pass of this analysis, that this budget is shared with every other AV endpoint Samurai might add later, is real but speculative: there is no other AV integration anywhere in the repo today, so it is future contention weighed against nothing, not a present cost.

**Reschedule freshness — not vendor-documented, and this document does not assert a claim it can't source.** No fetched AV page stated an update cadence or reschedule-handling commitment for `EARNINGS_CALENDAR`. This is a genuine open item, not a resolved one — flagged rather than papered over.

**Licensing — no automated-trading clause found.** Terms of Service §2 ("Grant of License"): personal, non-commercial use unless otherwise agreed, with "commercial use" triggered by acting on behalf of a business entity (§2.a.ii), redistributing to third parties (§2.a.iii), or having an active affiliation with a financial-industry employer (§2.a.iv) — not by trading on personal capital. No clause restricts automated/algorithmic use of the data itself.

**Verdict:** the strongest candidate found — the only one whose forward-looking behavior is proven by a live response rather than inferred from marketing copy, with an ample rate-limit margin and a schema that already carries the timing field #685 needs.

### Finnhub — `GET /calendar/earnings` — UNVERIFIED on the one axis that decides this filter, not recommended as-is

Fetched live 2026-08-26: [`finnhub.io/docs/api/earnings-calendar`](https://finnhub.io/docs/api/earnings-calendar), [`finnhub.io/pricing`](https://finnhub.io/pricing), [`finnhub.io/terms-of-service`](https://finnhub.io/terms-of-service).

**Forward-looking status on the free tier is contested by Finnhub's own documentation, and no independent source resolves it.** Two Finnhub-authored strings disagree with each other:
- The pricing page's comparison table (fetched live): *"Earnings Calendar — 1 month and real-time updates (US)"* on the Free All-In-One row.
- The endpoint's own internal doc metadata, scoped specifically to `/calendar/earnings` (not shared boilerplate — it sits next to endpoint-specific fields like `premium` and `examples`): `"freeTier":"1 month of historical earnings and new updates"` — which reads **historical**, not forward.

Both fetched documentation examples on the page use past-dated `from`/`to` ranges; neither shows a forward example. An unauthenticated demo call (the technique that resolved this cleanly for Alpha Vantage) is not available — Finnhub requires a registered API key, and creating an account was out of scope for this research pass. A targeted web search for third-party reports (GitHub issues, Stack Overflow) found free-tier users discussing the 1-month window but **no report explicitly confirming or denying that the free-tier window extends forward past today rather than only backward**. This is not a minor gap: it is the single requirement (#1 above) this whole filter exists to satisfy, and it is exactly the failure mode doc 22 and doc 32 both warn about — inferring vendor behavior from marketing copy instead of a verified response. Rather than resolve this in Finnhub's favor on the prettier of two conflicting Finnhub-authored strings, this document leaves it **unverified** and does not recommend Finnhub until it is checked against a real key (a $0 sandbox signup, deferred to implementation time rather than done in this research pass).

**The `hour` timing field is real but its enum is not confirmed.** The docs' own sample response shows one observed value, `"hour": "amc"`. No enumeration of the full value set (commonly guessed as `bmo`/`amc`/`dmh` before-market/after-market/during-market conventions elsewhere in the industry) was found documented on Finnhub's page itself — that convention is asserted by inference, not sourced, and should not be treated as confirmed until seen in Finnhub's own docs or a live response.

**Rate limit.** Free plan: **60 API calls/minute**, plus a **30 calls/second** cap layered on top of every plan (Terms of Service, "API Limit and Access": *"There is a 30 API calls/second limit on top of all plan's limit"*). This is the loosest limit of any candidate evaluated — genuinely a point in Finnhub's favor if the forward-looking question resolves positively.

**Licensing — no automated-trading prohibition found.** Terms of Service, "Redistribution Rights and Personal Use": *"You hereby agree to not redistribute or share access to data or derived results from the data obtained from Finnhub with anyone or any 3rd party without written approval from Finnhub. All plan[s] listed on Finnhub website [are] strictly for personal use unless explicitly stated otherwise."* The disqualifiers from the personal-use plan are narrow and enumerated: *"You are securities professional (registered with FINRA, SEC, CFTC or relevant regulatory bodies)... You are using this data for your business or registering under your business name... You are going to deduct this expense as a business expense."* Samurai — a private individual trading his own capital, per the same framing doc 22 already applied to Alpaca — trips none of the three. Unlike Trading 212 (doc 35), there is **no clause anywhere in this ToS naming algorithmic, automated, or programmatic trading use of the data**.

**Cost if the free tier is inadequate.** Not reached on rate limit or licensing. Paid tier exists ($3,500/mo "Contact Us" All-In-One) only for 20-year depth Samurai doesn't need for this filter — but if the free tier turns out to be historical-only, no amount of headroom on rate limit fixes that; the paid tier would be the only way to get Finnhub's better schema and looser limit with confirmed forward coverage.

**New integration, accepted cost if pursued.** No existing Finnhub key or client exists anywhere in `server/` (verified — `grep -rn -i finnhub server/` returns nothing outside this doc's citation). If a future implementation pass signs up for a free key and confirms the free tier returns dates past today, Finnhub becomes a strong second candidate on the strength of its rate limit alone; until then it should not be the pick.

### Financial Modeling Prep (FMP) — `earnings-calendar` — adequate but the one vendor with a real reschedule-honesty gap

Fetched live 2026-08-26: [`site.financialmodelingprep.com/developer/docs/stable/earnings-calendar`](https://site.financialmodelingprep.com/developer/docs/stable/earnings-calendar), [`.../pricing-plans`](https://site.financialmodelingprep.com/pricing-plans), [`.../terms-of-service`](https://site.financialmodelingprep.com/terms-of-service). Not in the original candidate list but surfaced by search as a credible free-tier competitor, so evaluated to the same bar.

**Forward-looking, confirmed, with a caveat the vendor states about itself.** `from`/`to` date-range params return future dates (FAQ, verbatim: *"Future earnings data is still available through the earnings-calendar endpoint, but you'll need to include both a from and to date in your request to retrieve it"*). But the same FAQ page admits the mechanism behind unconfirmed dates: *"For upcoming earnings without official dates, we use an estimation model based on historical patterns, which is updated once official dates are confirmed."* And, directly on point for reschedule-safety: *"What is the best way to filter earnings dates by confirmed dates only? — That's currently not possible."* There is no `date_status`/`confirmed` flag exposed in the response at all — contrast Massive's Benzinga endpoint below, which does expose exactly that field. FMP is the one candidate here where a rescheduled or still-estimated date cannot be distinguished from a confirmed one at read time.

**Rate limit.** Free "Basic" plan: **250 calls/day**, end-of-day data. Comfortably adequate for a 20-name daily pass.

**Licensing — same personal/non-commercial shape, no automated-trading clause,** but with broader "Commercial Use" language than Finnhub or Alpha Vantage. Terms of Service §2.2.1 defines Commercial Use to include *"Data Collection and Analysis for Commercial Purposes: Collecting, aggregating, or analyzing data using FMP Services or Data for commercial purposes or to support commercial activities, including market research, business intelligence, or **data-driven decision-making**"* — wording broad enough that a hostile reading could reach any trading system, though it is explicitly conditioned on the activity being "for commercial purposes," which is the same open "is Samurai commercial" question every other vendor here inherits, not a new one. No clause names algorithmic or automated trading specifically.

**Verdict:** adequate on rate limit, and forward-lookingness is vendor-stated (though, unlike Alpha Vantage's, not independently confirmed by a live call in this research pass) — but the missing confirmed/projected flag is a real, vendor-admitted gap against the "does the API reflect reschedules or go stale" requirement. Not recommended over Alpha Vantage.

### Massive (formerly Polygon.io) — `GET /benzinga/v1/earnings` — ruled out on cost, not on merit

Fetched live 2026-08-26: [`massive.com/docs/rest/partners/benzinga/earnings`](https://massive.com/docs/rest/partners/benzinga/earnings). Polygon.io rebranded to Massive on 2025-10-30 (`massive.com/blog/polygon-is-now-massive`); the old `polygon.io/docs/...` paths now 404.

This is the best-specified schema of everything surveyed — it explicitly exposes `date_status: projected | confirmed`, the exact reschedule-safety signal FMP lacks, plus `last_updated` timestamps. But the docs page states its own plan gate directly: *"Benzinga Earnings — $99/mo — Plan Access: Not included — available on select Benzinga expansion plans."* This endpoint is **not on Massive's base or free tier at all**; it's a paid Benzinga add-on regardless of which core Massive plan Samurai holds. Ruled out on cost — $99/mo for a once-daily 20-name check is disproportionate next to a working £0 alternative. Separately, `docs/research/30-data-vendor-decisions.md` and `docs/research/22-mi-source-licensing.md` §3 already carry an **open, unresolved licensing finding against this same vendor**: Massive's Businesses ToS has a derivative-works clause naming "investment strategy" over its OHLCV data, currently unresolved and already reaching shipped code as the equities data fallback. Adding a second, paid Massive product before that finding is closed would be compounding exposure to a vendor with a live open question, not just an unrelated cost decision.

### Nasdaq Data Link — ruled out, no free forward-looking product found

Checked live 2026-08-26 via [`docs.data.nasdaq.com/docs/getting-started`](https://docs.data.nasdaq.com/docs/getting-started) and the dataset catalog. Nasdaq Data Link's free tier is macro/reference data — *"a vast collection of free and open data collected from a variety of organizations: central banks, governments, multinational organizations and more"* — not corporate earnings calendars. Forward-looking earnings/estimates data on this platform is sourced from Zacks and sold as a-là-carte premium datasets with no self-serve published price (contact-sales tier). No free or cheap path found; ruled out without a paid quote to compare, since a free alternative already exists.

## Recommendation

**Alpha Vantage `EARNINGS_CALENDAR` on the free tier.**

It is the only candidate whose forward-looking capability was **proven by a live, dated response** rather than inferred from a vendor's marketing copy: a call made today (2026-08-26) using AV's own published, unauthenticated demo key (`apikey=demo`) against the real production endpoint returned earnings dated today and running forward across the requested 3-month horizon, with a real CSV schema (`symbol,name,reportDate,fiscalDateEnding,estimate,currency,timeOfTheDay`) that already carries the before/after-market timing field #685's session-labelling methodology needs. This is inference, not a vendor guarantee — the `demo` key is documented elsewhere on AV's site to return fixed/canned data for some functions, and no fetched page states that `EARNINGS_CALENDAR` is live for `demo` specifically — but the returned rows being dated exactly today, across a broad market-wide list rather than one fixed symbol, is evidence against a static/canned response and is the strongest signal any candidate in this document produced. The free tier's 25-requests/day cap is not a real constraint against this filter's ~1-call/day need, and its Terms of Service carry no clause restricting automated or algorithmic use of the data — only redistribution and professional/business status, neither of which describes Samurai's private, single-operator, own-capital posture (the same posture already accepted for Alpaca News in `docs/research/22-mi-source-licensing.md`). **It does not clear all four requirements**: reschedule freshness (requirement 3) is unverified for Alpha Vantage — no fetched page states an update cadence or reschedule-handling commitment for `EARNINGS_CALENDAR`, so this is a real, open gap being carried forward rather than resolved, not a point of superiority over FMP's vendor-admitted version of the same gap.

**Finnhub was the initial front-runner on paper — free-tier `GET /calendar/earnings`, a 60/min rate limit, a `hour` timing field, and no algo-trading clause — but its forward-looking claim on the free tier does not survive scrutiny of its own documentation:** the pricing page says "1 month and real-time updates," but the endpoint's own internal metadata says "1 month of **historical** earnings," and no forward-dated example or independent third-party confirmation was found for either reading. Getting this wrong is exactly the failure this document exists to prevent — a filter built on a feed that turns out to be historical-only would silently do nothing. Finnhub is not ruled out; it is **deferred pending a free-key signup and one live test call**, which was out of scope for this research pass (see doc 22/32's standing rule against inferring vendor behavior from documentation alone when a live check is possible — for Finnhub specifically it currently is not, without an account).

FMP is adequate on rate limit and forward-lookingness but is the one candidate that admits it cannot distinguish a confirmed release date from a still-estimated one. Massive's Benzinga earnings endpoint has the best schema of everything surveyed but costs $99/mo and adds a second exposure to a vendor with an already-open, unresolved licensing finding. Nasdaq Data Link has no free product in this space at all.

**Residual, inherited, not new:** whether Samurai's live-money, single-operator use is "personal, non-commercial" under any of these vendors' terms is the same open question `docs/research/README.md` already tracks as open item 2. This filter does not resolve it — it inherits the same read already applied to Alpaca News, and if that question is ever answered "commercial," it reopens Finnhub's licensing fit exactly as it would reopen Alpaca's.

**Not evaluated here, and deliberately out of scope:** implementation placement (candidate-pool-level filter vs. a later runtime veto), the session-labelling window itself, and whether an ADR is needed — #926 already recommends candidate-pool-level, no new ADR, and reuse of #685's corrected same-day/next-day methodology; those are implementation-ticket decisions, not vendor-selection ones.
