## Contradiction matrix

- **GAP-A — Two specs assert the 7-stage pipeline (with `invalidation` included) as current fact; five sources say it's 6 and unbuilt.** `debate-engine-spec.md` states outright: *"The Debate Engine sits between Analysts and Trader in the 7-stage pipeline... Analysts → Debate Engine → Trader → Invalidation → Risk Manager → Verdict → Execution"* — no "not yet built" qualifier. `cross-spec-contracts.md:75` (the **frozen registry**) says the same: *"The pipeline is SEVEN stages, not six."* Both contradict: `trader-spec.md`'s own diagram (*"Debate Engine → Trader → Risk Manager → Verdict → Execution"*, no Invalidation), `orchestrator-spec.md` (`TickOutcome.final_stage` has no `'invalidation'` member "deliberately... added only when invalidation ships"; composition root binds only 6 decision-path `TickSteps`), `shared-sqlite-store-spec.md` (`current_tick.stage` CHECK still lists 6 names), and CLAUDE.md (*"the runtime chain is six stages and goes Trader → Risk today"*). **Fix:** correct `debate-engine-spec.md`'s diagram line and `cross-spec-contracts.md:75` to state the pipeline *will be* seven stages once `invalidation` ships and is six today — matching the phrasing `orchestrator-spec.md` already uses correctly. The registry is the non-authoritative side here; CLAUDE.md and the majority of specs are right.

- **GAP-B — `devils-advocate-spec.md` calls itself a "tick" stage throughout; the current orchestrator model puts it on the decision path, a strictly less-frequent cadence.** The 2026-08-16 tick/decision split (`orchestrator-spec.md`) states: *"Tick ≠ decision. A tick fires on the tick interval (τ, default 2 minutes)... A decision fires once per debate bar and runs the full stage chain"* and explicitly: *"it is a decision-path stage, so it runs at most once per debate bar"* for `invalidation` by name. `devils-advocate-spec.md` predates the split (2026-08-05) and says "a **seventh tick stage**" (Solution, line 18), "**triggered ticks**" (Further Notes, line 386), and frames Trigger & Placement stories 1–4 entirely in tick language. This is not cosmetic: issue #718's own triage comment (in this repo's record) already flagged that under the split, the LLM cost is "once per decision per instrument," roughly **30× less** than a tick-based reading implies. **Fix:** reword "seventh tick stage" → "seventh stage of the decision chain" / "decision-path stage," "triggered ticks" → "triggered decisions," and note explicitly that the stage runs once per debate bar, not once per τ=2min tick — this is the framing an implementation ticket needs to get the cost/frequency arithmetic right from the start.

- **GAP-C — The one contract the spec's enforcement mechanism depends on was never added to `RiskInput`.** `devils-advocate-spec.md` (line 239, and `cross-spec-contracts.md` §8) both state `RiskInput` gains `invalidation?: InvalidationResult`. `risk-manager-spec.md`'s current `RiskInput` interface block is `{ trace_id, intent, clock, portfolio, breakers, next_breaker_state, mode }` — no `invalidation` field, and the string "invalidation" does not appear anywhere in the file. The Cross-Spec Ripple list at the bottom of `devils-advocate-spec.md` claims this ripple is owed but does not confirm it landed — it hasn't. **Fix:** this is the load-bearing seam (Risk hard-reject on a breached condition) — flag it explicitly as unimplemented rather than implied-done, so a `/to-tickets` pass doesn't assume the wiring point already exists.

- **GAP-D — `bar_timestamp` flooring: mandated by this spec, documented as a known unfixed defect in its own storage table.** `devils-advocate-spec.md` story 43 requires: *"`bar_timestamp` floored to the instrument's bar boundary... The flooring helper must be applied on write, and the same floored value must be used everywhere."* `shared-sqlite-store-spec.md` already has the `invalidation_log` table (content-addressed on `(instrument, bar_timestamp)`, matching the spec) but documents, unresolved: *"`bar_timestamp` on `invalidation_log` is not floored to the bar boundary at write time (mirrors the same defect on `debate_log`), which would break replay lookups."* This is exactly the failure mode `devils-advocate-spec.md`'s own Replay Behaviour section warns about — an unfloored write means a live tick at 14:32:07 writes 14:32:07 while a replay looks up 14:30:00 and silently gets `unavailable` instead of the real row. **Fix:** the flooring helper fix belongs to whichever ticket lands `invalidation_log` writes — should be sequenced with (or ahead of) the `debate_log` fix, since it's the identical bug, not a new one.

- **GAP-E — `BacktestReport.invalidation_replay` is asserted in prose but absent from the actual interface it should be on.** `cost-model-backtest-spec.md`'s "Module: Determinism" section states `BacktestReport` "gains an `invalidation_replay` attestation" (matching `devils-advocate-spec.md` story 47), but the file's own `BacktestReport` interface definition (`{ config_hash, seed, metrics, walk_forward?, capacity_ceiling, lookahead_audit }`) does not list it — an internal contradiction within `cost-model-backtest-spec.md` itself, not something `devils-advocate-spec.md` did wrong. **Fix:** add `invalidation_replay` to the type definition in that spec; low urgency since neither the stage nor the harness attaching to it is built yet, but worth fixing in the same pass that fixes GAP-C/GAP-D so `/to-tickets` doesn't need a second correction round.

- **GAP-F — Naming drift: `TickStatus.stage` vs. the type that actually exists.** `devils-advocate-spec.md` story 4 says: *"I want `TickStatus.stage` to report `'invalidation'`."* No spec defines a type named `TickStatus`; the actual type is `CurrentTick.stage` (`orchestrator-spec.md`, `current_tick` table). Likely a name that predates the 2026-08-16 tick/decision rework. **Fix:** rename to `CurrentTick.stage` in the spec text.
