## Breakage assessment — would applying the survivors keep the app intact?

Ordered by risk, not by value. "Safe" here means: no behaviour change for any input the system
currently handles correctly, and the existing 2,318-test suite is a sufficient gate.

### Carries real risk — needs care

**H1 (validate wire JSON) — the audit's "no new plumbing" claim does not fully hold. Verify
before applying.**

The audit argued that throwing an existing `*ProviderError` means the existing retry path
already handles it. That is true for *classification* but the propagation depends on which
consumer is upstream, and the two differ:

- **Bar/indicator path — contained.** A throw inside `persona.run()` is caught per-persona at
  `analysts/orchestrator.ts:165`, retried once, and degrades to an `AnalystFailure` → the
  specced role-dependent skip. This is the well-behaved case.
- **Any path outside the analyst layer — costs the whole tick, and defeats the overlap guard.**
  `SequentialTickRunner.runInstrument` has no try/catch by design (`tick-runner.ts:30` — a
  crash must leave the `current_tick` row stale). A rejection propagates to the worker at
  `tick-loop.ts:80`, and `runTickPlan` awaits `Promise.all` over the workers. `tick-loop.ts` is
  93 lines with **zero `try`/`catch` and no `AbortSignal`** — verified, not assumed.

  The first consequence is the obvious one: one instrument's parse failure aborts the remaining
  instruments in that tick. The second is not, and it is the reason this matters.

  `Promise.all` rejects on the first worker rejection **but does not cancel the other workers**
  — they are still mid-pipeline. The rejection reaches `runOnce` at `production.ts:1719`, which
  logs `tick failed` and then, in its `finally`, sets `inFlight = undefined`. That is the exact
  flag the *next* tick tests in its `"tick skipped: previous tick still running"` guard
  (`production.ts:1701`). **So the guard reports the tick as finished while its surviving
  workers are still running**, and the next scheduled tick starts alongside them whenever an
  orphaned worker outlives the remaining interval.

  Order duplication is very likely contained — `computeIdempotencyKey` is bar-derived and dedup
  layer 1 (`store.findByKey`) rejects a replayed key before the broker. **Spend is not.** Each
  orphaned worker continues to issue billed LLM debates against ADR-0008's $50/14-day cap, and
  nothing accounts for them as belonging to a tick already declared failed.

  This is **pre-existing, not introduced by H1** — but H1's entire effect on this path is to
  raise the throw rate on it, which is precisely the question asked here.

  Note also that `isRetryable*Error` gates on `status >= 500`, and a *parse* failure has no
  status — so it classifies as non-retryable and propagates on the first attempt.

**Recommendation:** apply H1, but at the two data-source inlets prefer *returning the typed
"no data" signal the port already has* over throwing, where one exists — `getQuote` returns
`Quote | null`, and `null` is already the port's "no bid/ask available" contract. Reserve the
throw for the paths whose only consumer is an analyst.

**Per-instrument isolation in `tick-loop.ts`'s worker is a precondition of applying H1, not an
optional extra.** Wrapping the `runInstrument` call so one instrument's throw becomes a failed
`TickOutcome` rather than a rejected worker fixes both consequences at once: the rest of the
tick survives, and `Promise.all` no longer settles early with workers still in flight. It is a
small change and it is worth having on its own merits — the orphaned-worker spend leak above is
live today, independent of H1. **This should be its own issue and its own PR, landing before
H1.**

**L2 (name the SELECT columns) — this is a deliberate behaviour change, not a no-op.**
The whole point is to convert a silently-`undefined` column into a loud SQLite error. If any
latent column-name mismatch exists today in one of the 13 sites, a read path that currently
appears to work will start throwing after the change. That is the correct outcome, but it must
be applied with the test suite as the gate and with the understanding that a *new* failure
surfacing is the fix working, not the fix breaking something. Apply per-module, not in one
sweep.

**F-5 (produce the risk critic) — not just code.** Wiring step 7 adds an LLM call to the risk
path on every evaluated intent. That interacts directly with ADR-0008's $50/14-day spend cap
and with the debate latency budget (#374/#392). It needs a cost estimate and a cadence decision
before implementation, and per Standing Pipeline Rule 1 it needs a wayfinder map — it is not a
drive-by. **It also has no issue; one should be filed regardless of when it is built.**

## One thing this triage found that the audits did not

Everything above is re-assessment. This is new, and it is live today independent of any fix
being applied:

**A tick that fails is declared finished while its other workers are still running.**
`Promise.all` in `runTickPlan` (`tick-loop.ts:80`) rejects on the first worker rejection without
cancelling the rest; `runOnce`'s `finally` (`production.ts`) then clears `inFlight`, which is
the flag the next tick's "previous tick still running" guard reads. The orphaned workers keep
running the full pipeline — including billed LLM debates against ADR-0008's $50/14-day cap —
attributed to a tick already logged as `tick failed`. Order duplication is contained by
idempotency; spend is not. See item 8.5 and the H1 breakage analysis for the fix.

The reason this went unseen is worth recording: it is the *inverse* of this repo's documented
defect class. The usual failure is a mechanism nothing calls. This is a mechanism that keeps
calling after everything upstream has concluded it stopped.
