## Contradiction matrix

- **GAP-1 — trader-spec.md still describes `DebateResult.direction`/`debate_id` as missing, but debate-engine-spec.md already added them.** Registry §1/§2 required Debate Engine to add `direction: 'bullish'|'bearish'|'neutral'` and a deterministic `debate_id` to `DebateResult` (impl ticket #24). debate-engine-spec.md's own extraction confirms both fields exist verbatim: `direction` ("structured signal, distinct from the free-text `position`") and `debate_id: string // deterministic = hash(instrument + bar + AnalystView set) ... reconciled in impl ticket #62`. But trader-spec.md still reads: *"The Trader consumes DebateResult and, being mechanical (no LLM), needs two fields the current Debate Engine contract does not provide... This must be reconciled into the Debate Engine spec and its implementation tickets (#24 Domain Types & Contracts) during the cross-spec verification pass — do not build the Trader on an unstated contract."* This is stale — the reconciliation already happened on the Debate Engine side and trader-spec.md's text was never updated to drop the "not yet present" framing. **Fix:** edit trader-spec.md's Consumes section to state `DebateResult.direction`/`debate_id` are defined (cite debate-engine-spec.md directly), removing the "must be reconciled" language so a ticket-writer doesn't treat this as still-open.

- **GAP-2 — trader-spec.md presents full position-aware branching as required MVP scope, contradicting wayfinder decision #224.** Issue #224 (closed 2026-07-28) explicitly resolved: *"enter/hold-only is sufficient for the first paper run. #74 (position-aware branching: scale-in/exit-flip/hold) is deferred as a fast-follow, not a blocker."* orchestrator-spec.md correctly reflects this (references #74 as non-blocking, does not itself implement branching). But trader-spec.md's Solution section lists *"Position-aware — reconciles the new debate against current holdings before acting"* as a core architectural decision, user stories 20–23 spec entry/scale_in/exit/hold routing as first-class requirements with no phasing language, `OrderIntent.intent_type` includes `'scale_in'`/`'exit'` in its core (non-optional) union, and the Testing Decisions section requires MVP test coverage for *"entry / scale_in / exit / flip / hold-null."* Nothing in trader-spec.md marks this as deferred or fast-follow. **Fix:** either (a) add an explicit phasing note to trader-spec.md scoping scale-in/exit-flip to a v2/fast-follow ticket (matching #224 and keeping #74 open for exactly that), or (b) if trader-spec.md's fuller scope was intentionally decided after #224 closed, get that decision recorded as a new addendum on #224 or a follow-up issue — right now the two documents give a ticket-writer contradictory MVP boundaries for the same component.

- **GAP-3 — trader-spec.md's own `intent_type` union doesn't include the `flip` value its Testing Decisions section requires testing.** `OrderIntent.intent_type: 'entry' | 'scale_in' | 'exit'` has no `'flip'` member (a directional reversal is modeled as two separate decisions: exit, then a fresh entry — explicitly by design). But the Testing Decisions section lists *"entry / scale_in / exit / flip / hold-null"* as routing cases to test. Internal inconsistency within one spec file. **Fix:** remove `flip` from the Testing Decisions list (replace with "exit followed by a subsequent entry decision, tested as two cases") to match the actual type union.

- **GAP-4 — risk-manager-spec.md's "fully mechanical, no LLM" framing contradicts its own Risk Critic module.** Lines 11/19 state *"It is the stage that must be trusted absolutely under stress, which is why it is fully mechanical and deterministic"* and *"Fully mechanical, deterministic, no LLM — reproducible and backtestable."* But the Risk Critic module (added via ADR-0003, resolving wayfinder map #186) is *"a single red-team LLM pass over the intent... may trim or hard-reject, same authority as the mechanical steps above."* An LLM with binding trim/reject authority is not "no LLM" — the framing sentences predate the Risk Critic addition and were never updated to acknowledge it. **Fix:** rewrite the Solution-section framing to something like "the mechanical core is fully deterministic; the Risk Critic is the one bounded, advisory-but-binding LLM step, isolated behind its own module" — so a reader doesn't take the opening framing at face value and then hit a contradiction three sections later.

- **GAP-5 — risk-manager-spec.md has a second, smaller internal inconsistency: a stale reference to "v1 static concentration buckets."** Line 147 states the concentration check was corrected 2026-07-26 from static v1 buckets to a dynamic pairwise-correlation matrix (explicitly flagged in-spec as a correction of a stale draft). But line 168 (CII module) still says the static instrument→country mapping *"lives alongside the v1 static concentration buckets (Check Pipeline step 6)"* — not updated in the same pass. **Fix:** update line 168's parenthetical to reference the dynamic correlation-matrix step by its corrected name.

- **GAP-6 — circuit-breaker / anti-overfitting kill-line thresholds are specced as tunable config in two places, not fixed constants, contradicting the binding research constraint that these must be fixed.** This was already flagged MEDIUM in the frozen registry ("PBO 0.05 kill-line exposed as tunable config... risks the one hard kill criterion being softened") and remains unresolved — cost-model-backtest-spec.md still has an internal split on this point: the interface comment and body text state *"Reject if PBO > 0.05"* as if fixed, while the Out of Scope section says *"the MinBTL constant, the PBO threshold value... are config, with pessimistic defaults."* The same pattern now also appears in risk-manager-spec.md: *"Exact thresholds are config, tuned in paper trading"* and *"all caps and breaker thresholds are config, tuned in paper trading; not fixed here"* for the portfolio-drawdown and kill-switch circuit breakers. Escalating from the registry's original MEDIUM to **HIGH** here because it now spans two independently-specced safety gates (backtest overfitting kill-line AND live circuit breakers), not one. **Fix:** decide explicitly, once, for both specs: either the numeric values are genuinely fixed constants in code (not reachable via any config surface), or they're config with a hard floor/ceiling enforced in code so no config change can cross the research-mandated line (e.g., PBO threshold config value is clamped to ≤0.05, drawdown breaker clamped to ≤ some fixed max). Record the decision in cross-spec-contracts.md so it stops re-appearing per-spec.

## Security findings

**HIGH:**
- **risk-manager-spec.md leaves fail-open vs. fail-closed on a Risk Critic API failure explicitly undecided**, despite the Risk Critic having "same authority as the mechanical steps" (binding trim/reject power). Spec's own words: *"Not yet decided (deferred to implementation tickets): ... fail-open vs fail-closed behavior on a critic API failure."* An undecided default on a binding safety gate is exactly the kind of gap that shouldn't ship to `/to-tickets` silently — a ticket that "implements the Risk Critic" without this decision made risks an implementer picking fail-open by accident (e.g., via a try/catch that swallows the error and proceeds). **Fix:** resolve this now — recommend fail-closed (critic-unavailable ⇒ treat as `reject`/`trim-to-minimum`, since the mechanical steps alone were the pre-#186 safety baseline and reverting to that baseline on critic failure is the conservative default) — and record it as a decision, not an implementation-ticket footnote.
- **execution-spec.md's broker-credential/mode guard is a single acknowledgment, not a control.** The entire extent of key-handling discussion is: *"the broker credentials/config (ops: trade-only, withdrawals disabled, IP-whitelisted per CONTEXT.md invariant 3)."* There is no described guard preventing e.g. a `mode: 'backtest'` run from being pointed at live credentials by misconfiguration, no mention of separate paper/live key sets being enforced at the code level (only at the SQLite-file level, per shared-sqlite-store-spec.md's one-file-per-environment design). **Fix:** add an explicit assertion/guard in execution-spec.md: `BrokerAdapter` construction validates that the credential set's account type matches `ExecutionInput.mode` (e.g., reject startup if `mode==='live'` but the configured Alpaca key is a paper key), failing closed (refuse to start) on mismatch.
- **execution-spec.md's crash-restart resubmit path has an undescribed race-condition risk.** Reconciliation's rule is *"never placed → resubmit or mark `rejected`"* — but if the original submit succeeded at the broker and just isn't yet visible via `getOrder` (in-flight, not yet queryable), a naive "not found ⇒ resubmit" could double-submit a real order. The spec doesn't describe a grace/settle window or an intermediate "recently submitted, awaiting first confirmation" state before deciding to resubmit. **Fix:** add an explicit settle-window rule to execution-spec.md's reconciliation module — e.g., only resubmit if the write-ahead `pending` row is older than N seconds/one broker round-trip AND a fresh `getOrder`/`getOpenPositions` call still shows nothing, not on the first reconciliation pass after a restart.

**MEDIUM:**
- **feedback-loop-spec.md's `ApprovalChannel` (risk-threshold-loosening approvals, breach alerts) has no described authn mechanism.** It says only that the pattern should "mirror Verdict and Risk," without confirming it reuses Verdict's newly-hardened HMAC-signed `SignedApprovalChannel` (issue #229) rather than a second, separately-implemented (and possibly unauthenticated) channel. **Fix:** state explicitly in feedback-loop-spec.md that FL's `ApprovalChannel` is the same type/interface Verdict defines and hardened, not a parallel implementation.
- **dashboard-spec.md doesn't address output-escaping for debate/analyst free text.** The dashboard renders `DebateLog` content (potentially LLM-generated rationale) per user story 3, but nothing in the spec discusses HTML-escaping vs. raw interpolation for that content in the inline HTML page. Low likelihood of actual attacker-controlled content reaching this path today, but the spec is silent on the mitigation, not explicit that it's handled. **Fix:** state the templating/escaping approach (e.g., "all free text is HTML-escaped before interpolation; no `innerHTML`/raw-string templating of ingested text").
- **shared-sqlite-store-spec.md specifies no file-permission requirement for the SQLite DB file(s)**, despite them holding `closed_trades.realized_pnl_net`/`open_positions`/`fills` — real trade/PnL data CLAUDE.md requires tracking for HMRC/CGT purposes. **Fix:** add a line requiring owner-only file permissions (e.g., `chmod 600`) on `data/samurai-{env}.sqlite`.
- **shared-sqlite-store-spec.md doesn't address DB-level failure modes** (SQLITE_BUSY/lock contention, disk full, file corruption) beyond WAL+`synchronous=FULL`, which protects against crash-mid-write but not the other three. CLAUDE.md explicitly names power/WiFi drops and lid-close as host risks this system must survive on the MacBook deployment target. **Fix:** add a short failure-mode section — at minimum, a stated retry/backoff policy on `SQLITE_BUSY` and an explicit (even if "out of scope for v1, manual recovery") statement on corruption/disk-full behavior, so it's a documented gap rather than a silent one.

**LOW:**
- Data-source/news-source API-key handling (Alpaca/ccxt/IBKR market-data credentials, Market Intelligence news-API credentials) is punted as "ops/setup, out of scope" identically across market-data-service-spec.md, market-intelligence-spec.md, and (by omission) analysts-spec.md. Lower severity than broker trading keys (no fund-movement risk), but worth one consolidated ticket rather than three separate specs each disclaiming it individually.

## Design-practice findings

**MEDIUM:**
- **execution-spec.md's `ReconcileReport` return type is declared but never given a field list anywhere in the document.** `reconcile(): Promise<ReconcileReport>` is called out as crash-safety-critical (store-vs-broker reconciliation), but nothing downstream (Dashboard, tests, `/to-tickets`) can build against its actual shape yet. **Fix:** enumerate `ReconcileReport`'s fields (at minimum: divergences found, corrections applied, count of orders resubmitted/marked-rejected) before this becomes a ticket.
- **dashboard-spec.md's `buildSnapshot` has no partial-failure/degradation story.** If any one of the eight `DashboardQueryStore` methods throws (e.g., a transient SQLite lock, or `getMark` failing for a delisted instrument), the entire `/api/snapshot` response fails — taking down positions, debates, verdicts, and performance views all at once instead of degrading per-section. **Fix:** wrap each section's fetch independently in `buildSnapshot`, returning a per-section error/null rather than propagating one failure to the whole response.
- **shared-sqlite-store-spec.md's `audit_log` table has no primary key or uniqueness constraint**, unlike every other append-only table in the same file (`bars`, `cii_snapshots`, `fills`, `closed_trades`, `debate_log` all have explicit PKs). **Fix:** add a PK (e.g., `(trace_id, stage, timestamp)` or a surrogate autoincrement ID) so a retried/duplicated write is at least structurally catchable.

**LOW:**
- feedback-loop-spec.md doesn't name the already-implemented `debate-attribution-lookup.ts`/`getContributionsForAttribution()` module (confirmed present in the codebase via the project's knowledge graph) — the spec describes the attribution join only in prose ("joined by debate_id"). Not a contradiction, just spec text lagging behind implementation naming. **Fix:** name the concrete module in the spec so future readers don't have to guess whether it exists.
- No spec formally owns/defines the injected `Clock` type that analysts-spec.md, trader-spec.md, risk-manager-spec.md, verdict-spec.md, market-data-service-spec.md, and cost-model-backtest-spec.md all consume — it's implemented at `src/shared/clock.ts` (`Clock`/`SimulatedClock`) but has no spec-of-record. **Fix:** add `Clock` to cross-spec-contracts.md's registry as a formally-owned shared type (owner: cost-model-backtest-spec.md, per its "this component owns the simulated Clock every stage injects" framing), closing the documentation gap even though the code already works.
- execution-spec.md hedges forced-liquidation ownership between two possible owners: *"a separate emergency module or Execution."* Not urgent for the first paper run (no live circuit-breaker trip expected in a smoke test), but this is a live-money-critical decision left unresolved. See Open Questions below.

## Performance / maintainability / complexity / simplicity findings

**MEDIUM:**
- risk-manager-spec.md's concentration check was upgraded from static v1 buckets to a dynamic pairwise-Pearson-correlation matrix (O(n²) per `evaluate()` call, in the synchronous hot path immediately before Verdict). Reasonable at small portfolio sizes, but combined with the new Risk Critic's LLM round-trip in the same stage, the latency budget for this stage has grown twice in the same spec revision without a restated end-to-end budget number. Not flagged as broken, just worth re-stating the total Risk-stage latency budget given both additions.

**LOW:**
- market-intelligence-spec.md specs a full six-type convergence-signal taxonomy and a spatial-clustering algorithm (grid-indexed union-find + haversine + weighted diversity bonus) for v1, with four of six signal-confidence formulas left as "unpinned config, tuned in paper trading" — i.e., the full complexity surface ships before any tuning data exists to justify the specific thresholds. Not blocking, a candidate for trimming to the two pinned signal types (`convergence`, `triangulation`) for the first paper run and adding the other four once there's real data to tune against.
- shared-sqlite-store-spec.md's single shared file across 6+ stages is a known, self-flagged, explicitly-deferred write-contention risk (not adopted/resolved in v1, correctly deferred to "Future Extensions"). Appropriately scoped as YAGNI given tick-based (not HFT) cadence — noted here only so it isn't forgotten once ingestion volume grows.
