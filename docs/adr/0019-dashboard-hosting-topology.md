# ADR-0019 — Dashboard stays co-located, LAN-only

- **Status:** Accepted
- **Date:** 2026-08-27
- **Decided by:** David — grilled live in [Grilling: dashboard hosting topology + auth](https://github.com/dd-jp/samurai-trading-system/issues/589), 2026-08-27
- **Related:** [#589](https://github.com/dd-jp/samurai-trading-system/issues/589) (this decision's grilling ticket), [#887](https://github.com/dd-jp/samurai-trading-system/issues/887) (the auth guard this topology depends on), [ADR-0007](0007-fully-automatic-execution.md) (no operator in any decision path), [ADR-0013](0013-no-human-gate-anywhere.md) (every human gate removed), [ADR-0010](0010-dashboard-vite-react-rewrite.md) (framework), `docs/research/40-dashboard-framework-and-hosting.md` §4.3/§8 (the option ranking and ADR title this record adopts)

## Context

The dashboard has been reachable only from the machine it runs on since ADR-0010. Whether that should change — reachable remotely, and if so how — was never decided; `docs/adr/` ran 0001–0018 with no hosting-topology entry, and #589 tracked the gap since 2026-07.

Two things narrowed the question before it reached David. ADR-0013 removed every remaining human gate (breaker re-arm, risk-threshold loosening both automatic), on top of ADR-0007's baseline that no operator sits in any decision path — so **no action a human takes through the dashboard is one the system waits on.** Unreachability delays *knowing*, never *doing*. Separately, alerting is an independent transport with compiler-enforced channel coverage (`AlertChannelSlots`), so "how do I find out something is wrong while I'm out" already has an answer that isn't hosting topology. A research pass on #589 (2026-08-19) verified both premises directly against the working tree: the client has exactly one network primitive (`useSnapshot.ts`, a bodyless GET), the two buttons in the whole client are local-state-only, and the server rejects every non-GET method with 405 — nothing displayed can be acted on through the dashboard.

The same research pass also surfaced a countervailing fact: `server/apps/supervisor/supervisor.ts` ties the dashboard and orchestrator processes together — either dying takes the other down. So the dashboard is not a free-standing observability layer; a co-located host is unreachable exactly when the orchestrator itself has stopped, which is also the moment someone would most want to look.

Auth was the other live half of #589's scope and was split out to #887 on 2026-08-19, since it binds regardless of how this decision landed: `GET /api/snapshot` ships with no auth, gated only by `HOST`'s unset-env-var default (`server/apps/service-api/index.ts:38`).

## Decision

**The dashboard stays co-located with the orchestrator. It is not remotely reachable — no tunnel, no VPN overlay, LAN-only.**

David's ruling, taken live against the case above: the dashboard need not be reachable when the Mac is off. The intraday horizon (ADR-0014) makes this cheaper than it would have been under the old multi-day horizon — the interesting window is a single session, concentrated in market hours, so "reachable when the Mac is off" mostly means "reachable when there is nothing running to observe" anyway.

Exposure beyond localhost, once it exists, is **LAN-only** — reachable from other devices on the same home network, no Cloudflare Tunnel, no Tailscale. This was chosen over doc 40 §4.3's top-ranked Cloudflare Tunnel + Access specifically to avoid routing live positions and P&L through a third party's edge, and over Tailscale to sidestep its Personal tier's individual/homelab framing for a live-money console. LAN-only exposure still requires #887's fail-closed bind guard to land first — the guard binds independent of this decision, but LAN-only is the concrete case it exists to gate.

> **SHIPPED 2026-09-02 — see the amendment below.** "Still requires ... to land first" is no longer true: #887's guard is landed and enforced. Read this paragraph as the case the guard gates, not as an open precondition.

## Consequences

- **The store stays local SQLite, undecoupled.** No hosting-topology change forces the store migration doc 40 §4.4 priced for a decoupled host.
- **Dashboard downtime tracks orchestrator downtime**, confirmed rather than assumed: the supervisor's shared-fault-domain coupling means a dead dashboard process is also a dead trading process. This is acceptable *only because* the alert path — not the dashboard — is the load-bearing observability channel. If the alert path is ever weakened or removed, this decision's premise weakens with it and #589's reachability question should be re-grilled.
- **Remote monitoring is out of reach entirely**, not just deferred behind a cost. Checking positions from outside the home network requires being on the LAN (e.g. via home VPN/router-level access set up independently of this system) or waiting until back at the machine.
- **#887's implementation now has an unblocked answer to its own open question** ("which ADR does the auth decision record against") — it points here, and its LAN-only guard work can proceed without waiting on a tunnel/VPN integration that this decision rules out.

## Alternatives considered

- **Cloudflare Tunnel + Access** — doc 40 §4.3's top rank; identity enforced at Cloudflare's edge before the request reaches Node, so no application code owns auth. Rejected: live positions and P&L would transit a third party's edge even though the tunnel itself is outbound-only, for a system whose whole premise is a small live book that does not need remote convenience badly enough to accept that.
- **Tailscale** — private overlay, no third-party data path for the traffic itself. Rejected: Tailscale Personal's terms frame the product for individuals and homelabs, a closer commercial-use question for a live-money trading console than doc 40 originally examined, and the reachability case for remote access was already weak once ADR-0013's "nothing waits on a human" argument held.
- **Decoupled host** (the branch #589 was filed to weigh) — reachable independent of the orchestrator's own process health. Rejected on the same grounds Vercel was rejected for originally (read-only FS, archived-function lifetime) plus the store-migration cost of moving off local SQLite, now confirmed unnecessary since nothing acted on through the dashboard needed that reachability.

## Amendment — 2026-09-02: #887's fail-closed bind guard ships

- **Related:** [#887](https://github.com/dd-jp/samurai-trading-system/issues/887) (the ticket this amendment closes out), `server/apps/service-api/bind-guard.ts` (the guard), `server/apps/service-api/server.ts` (where it is wired into `createDashboardServer`)

**This is the ADR #887's implementation cites as its own open question's answer** (see Consequences above). The guard this Decision's LAN-only paragraph depended on is now landed: `createDashboardServer` refuses to start when `host` resolves to anything other than the literal loopback addresses `127.0.0.1` / `::1` **and** the `SAMURAI_DASHBOARD_TOKEN` env var is not configured. Both halves are required — a non-loopback bind alone does not refuse (a credential can be set to permit it), and a missing credential alone does not refuse (the loopback default, which is every `yarn dashboard` invocation today, must keep starting). `bind-guard.ts` carries the full rationale, including why `localhost` is deliberately excluded from the allowlist (a hostname to resolve, not a literal address) and why the guard is structural — wired once inside `createDashboardServer` rather than duplicated in `index.ts` and `fixture-server.ts` separately, so both entry points (and every test) are covered by construction.

**Boot-time only, not request-time.** A configured `SAMURAI_DASHBOARD_TOKEN` unlocks the bind at startup; nothing in this repo yet verifies that value against any individual request to `/api/snapshot`. A bearer-token-checked-per-request design (#887's option 2) was considered and explicitly not chosen — this amendment ships option 1 only. Request-time verification, should LAN-only reach ever need it, is a separate, unshipped follow-up, tracked as [#1038](https://github.com/dd-jp/samurai-trading-system/issues/1038).

**On the stale citation this amendment also closes:** the Context section above cites `server/apps/service-api/index.ts:38` for the pre-guard `HOST` default. Checked against the tree: that citation was off by one **as written** on 2026-08-27 — line 38 was `const port = Number(process.env.PORT ?? 8787);` even then, and the `HOST` default has always been line 39, both before this amendment's changes and after (this amendment's PR inserted new lines *after* 39, moving nothing at or above it). This amendment leaves the citation unedited rather than correcting it — rewriting a decision record's own citation would misrepresent what the record said about the tree at the time it said it (`server/tools/check-path-citations.ts`'s stated design principle, and `docs/adr/` is exempted from the citation checker for exactly this reason). Read the Context section's citation as historical and always slightly wrong, not as a citation this change disturbed; the current default lives in `server/apps/service-api/index.ts` and the guard itself in `server/apps/service-api/bind-guard.ts`, neither pinned to a line number here on purpose.

**Unchanged by this amendment:** the Decision itself (dashboard stays co-located, LAN-only, no tunnel/VPN) and every other Consequence above. This amendment only retires the "guard not yet landed" precondition.

## Amendment — 2026-09-09: #1038 ships request-time verification (#887 option 2)

- **Related:** [#1038](https://github.com/dd-jp/samurai-trading-system/issues/1038) (the ticket this amendment closes out; David's 2026-09-08 decision comment on it is the ruling implemented), `server/apps/service-api/request-auth.ts` (the check), `server/apps/service-api/server.ts` (where it is wired), `server/apps/service-api/bind-guard.ts` (the boot-time half this amends alongside, and the source of the shared `isConfiguredCredential` rule both checks apply)

**Corrects the amendment directly above.** Its "Boot-time only, not request-time" paragraph said a bearer-token-checked-per-request design (#887's option 2) "was considered and explicitly not chosen" and that request-time verification was "a separate, unshipped follow-up." That was accurate on 2026-09-02 and is no longer: David's 2026-09-08 decision on #1038 shipped option 2, on top of — not instead of — the boot-time guard the previous amendment describes. Read that paragraph as historical from this point on, describing the gap as it stood before this amendment, not the current behaviour.

**What actually verifies what, now.** Two checks read the same `SAMURAI_DASHBOARD_TOKEN` for two different questions:

- `bind-guard.ts`'s `assertBindAllowed` (unchanged by this amendment) decides, once, whether the **process** may bind beyond loopback at all.
- `request-auth.ts`'s `isAuthorizedRequest` (new) decides, on every request to `GET /api/snapshot`, whether that **request** may read the book — a constant-time (SHA-256-then-`timingSafeEqual`) comparison against the bearer token in the request's `Authorization` header, refusing with `401` when the header is missing, malformed, or wrong, and applied **regardless of host** — symmetric with `isBindAllowed`'s own host-independence, and the only design that lets loopback-bound test coverage exercise the refusal path David's decision named as load-bearing (a test asserting only the accept-with-valid-token case would still pass against the pre-#1038 behaviour, which accepted every request unconditionally).

**Scope decision recorded explicitly, per #1038's own acceptance criterion: the static bundle is NOT covered.** Only `GET /api/snapshot` is gated. The dashboard's HTML shell and its Vite-built JS/CSS/font assets carry no book data — every number on the page arrives solely through the polled `GET /api/snapshot` (`client/src/hooks/useSnapshot.ts` is the client's one network primitive). Gating the shell too would break the client outright: a plain browser navigation to a shared link, and the `<script>`/`<link>` subresource requests that HTML then issues, carry no custom header, so an authenticated shell would 401 before any JavaScript ran to attach one. Serving the shell unauthenticated and gating only the data is the deliberate, narrower answer.

**How the client supplies the token, since the dashboard is its only consumer (#1038's other named acceptance criterion).** There is no login form. An operator shares a link carrying `?token=<value>`; `client/src/lib/dashboard-token.ts` reads it once, persists it to `sessionStorage` (tab-scoped, not `localStorage` — a bearer credential for the live book should not silently outlive the tab that captured it), and `App.tsx` immediately scrubs the query param off the address bar via `history.replaceState` (preserving the path, every other query param, and the hash tab-state lives in). This keeps the token out of the poll request's referrer and out of the URL visible after the first paint — it does not keep the token off the browser's history entry from the initial navigation (`replaceState` rewrites only the current session-history entry, not a prior visit) or out of the `Referer` header on same-origin subresource requests the HTML shell issues before React mounts (the client loads no third-party resources, so that referrer never leaves the dashboard's own origin). Every later poll in the tab — and every reload, via the persisted value — sends `Authorization: Bearer <token>` (`useSnapshot.ts`'s `authToken` option).

**The default, no-credential path is unchanged and still the norm.** With `SAMURAI_DASHBOARD_TOKEN` unset, `isConfiguredCredential` reads it as not-configured, `isAuthorizedRequest` returns `true` unconditionally, and every request — with or without an `Authorization` header — is served exactly as before this amendment. Every `yarn dashboard` invocation today, and every existing test that never set the env var, is this path.

**Unchanged by this amendment:** the Decision (co-located, LAN-only, no tunnel/VPN), every Consequence above, and the 2026-09-02 amendment's account of the boot-time guard itself — only its now-stale "not chosen"/"unshipped" characterization of request-time verification is superseded here.
